# Session Notes — 2026-05-16 (Session C)

## Context
Continuation of 2026-05-16 Session B (review + planning only). This session implemented
**Phases A, B, and C** of `CLAUDE/Docs/implementation_plan_2026-05-16.md`. Baseline at start:
10 suites, 222 tests green. End: 10 suites, 228 tests green.

## What Was Done

### Phase A — Correctness fixes
- **A1** — `CombatResolver.apply_combat_result`: dropped the `not attacker_died` clause from
  the `def_exp` calculation so a unit that counter-kills its attacker earns kill-tier EXP.
  Regression test added to `test_combat.gd` (counter-kill awards 30 EXP).
- **A2** — `GameState._snapshot_unit_data` / `_restore_unit_data`: deep-copy each
  `InventoryEntry` individually (`entry.duplicate(true)` per element). `Array.duplicate(true)`
  copies the array but shares Resource references, so combat use/durability had been mutating
  the Retry snapshot. 3 regression tests added to `test_snapshot_coverage.gd`.
- **A3** — Null-check `load()` results before `.duplicate()` in `GameState.load_default_roster`
  and `GameMap._spawn_units`; `push_error` + `continue` on failure.
- **A4** — Converted data-validation `assert()`s to `push_error` + `continue` in
  `DataManager._validate_cross_references` (×2), `GameMap._spawn_units`,
  `GameState.load_default_roster` — so bad data survives release builds (assert is stripped).

### Phase B — `-1 = infinite` uses sentinel
- **B1** — Added `InventoryEntry.has_uses()` (`uses_remaining != 0`). Routed usability checks
  through it (`Unit._find_equipped_weapon`, `ActionMenu`, `ItemMenu`, `MapCursor._use_item`
  fallback). Guarded both decrement sites (`Unit.use_weapon_durability`, `ItemHandler.apply_item`)
  to skip decrement/removal when `uses_remaining == -1`. `ItemMenu` shows ∞ for infinite items.
  Tests: `-1` weapon never breaks (`test_unit_stats.gd`); `-1` item never consumed
  (`test_skill_item_handler.gd`).
- **B2** — Set `uses_remaining = -1` on the lance + vulnerary in
  `data/roster/default/unit_01_soldier.tres` (verified it carries both before editing).

### Phase C — Settings architecture + New Game screen
- **C1** — New `scenes/ui/NewGameScreen.tscn` + `scripts/ui/NewGameScreen.gd`: an overlay child
  of `MainMenu` (open()/hide() like SettingsScreen) with permadeath (Off/On), leveling method
  (Random/Fixed), Start, Back. `MainMenu` "New Game" now opens it; Start writes the rules onto
  `GameState`, loads the roster, and changes to `GameMap`. All `@onready` paths validated with
  the godot-analyzer MCP `validate_onready_paths` tool.
- **C2** — Removed `permadeath` / `leveling_method` from `SettingsManager` (vars, load, save,
  reset) and the permadeath option from `SettingsScreen` (+ its `.tscn` node). Deleted
  `GameState._ready()` entirely — it only existed to pull those from SettingsManager; this also
  removes one autoload-ordering workaround. `GameState` keeps the fields with defaults for the
  direct-boot dev path. Old `settings.cfg` files keep harmless stale keys (no migration).
- **C3** — `PhaseBanner._on_phase_changed` now early-returns when `phase_banner == "skip"`
  (confirmed PhaseBanner is live-instanced in `GameMap.tscn` first). Added global UX setting
  `mouse_targeting` (`snap`/`disabled`) to `SettingsManager` + a `OptMouseTargeting` OptionButton
  in `SettingsScreen` ("Snap to Target" / "Keyboard Only"). Hid the inert `OptCombatAnim` control
  (`visible = false`) since no combat-animation system exists yet; the SettingsManager field is
  kept for later.
