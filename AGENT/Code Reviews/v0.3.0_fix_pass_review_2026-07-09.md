## F1 (HIGH) - Maximized readout has no live refresh trigger; the stale-label symptom likely survives

`b8e728b` routed the readout through `_applied_size_text()` and taught it
`Maximized (WxH)` — but nothing calls `_refresh_applied_size()`
(`scripts/ui/SettingsScreen.gd:452`) when the window maximizes.
Its only triggers are:

- screen open (`SettingsScreen.gd:256`),
- preset apply/revert (`:386`, `:399`),
- `resolution_written_back` (`:434-440`).

Maximize emits none of these: `resize_write_back_action` returns `"ignore"`
for `WINDOW_MODE_MAXIMIZED` (`scripts/autoloads/SettingsManager.gd:526` —
correct, per Q4 persistence stays untouched), so `resolution_written_back`
never fires. Un-maximize takes the `"restore"` branch → `_apply_display()`
re-requests the saved size, and `apply_resize_write_back`'s own-resize guard
(`SettingsManager.gd:539`) makes that a deliberate no-op — again no emit.
The coalesced resize hook does reach `SettingsScreen.apply_menu_scale()`
(`SettingsScreen.gd:293`), but that only re-anchors rows; it never touches the
readout label.

So the tester's exact flow — Settings open, press the OS maximize button,
watch the readout — still shows the stale `client WxH`
(`v030_resize_maximized_stale_client_readout_2026-07-08.png`), and a stale
`Maximized (WxH)` lingers after un-maximize. The fix only changes what renders
*when a refresh happens*; opening Settings while already maximized is the one
path that works. The headless assertion in `test_settings_screen.gd` pins the
formatter, not the trigger, so the suite stays green across this gap — the
triage plan's "shows live `Maximized (WxH)`" claim is stronger than what
landed.

**Recommendation:** subscribe SettingsScreen to
`get_viewport().size_changed` (deferred + gated on `visible`, mirroring
SettingsManager's own coalescing at `SettingsManager.gd:472`) and call
`_refresh_applied_size()`. That single trigger covers maximize, un-maximize,
AND makes the readout self-healing for the still-open one-axis-drag question.
Soften the triage-plan/GDD_07 wording ("formatter fixed; live trigger
pending") if the rerun build cuts before this lands.

## F2 (HIGH) - Settings still has no controller directional repeat; the section-1 complaint is only half-addressed

The tester's section-1 quote has two halves: focus can't reach off-screen rows
(fixed — `follow_focus = true`), and "The menu also doesn't have any
directional repeat" — said about the **Settings** menu. `MenuRepeatPolicy`
landed with a ui_* constructor documented for engine-focus screens (and
`test_menu_repeat_policy.gd:31-33` pins it), but its only consumers are
`ActionMenu` and `UnitDetailsScreen` — the V030-GP-02 custom menus. Settings
(engine focus navigation) still moves exactly one row per d-pad press with no
joypad echo. Long option lists + working scroll-follow makes this MORE
noticeable, not less.

The triage plan's GP-01 STATUS ("scroll-follow + menu-repeat portions FIXED")
conflates the two repeat sites; the rerun checklist row for section 1 will
test Settings repeat and find it absent.

**Recommendation:** either (a) land the Settings half before the rerun — in
`ModalScreen` (or SettingsScreen alone), consume `ui_up`/`ui_down` pressed
events the way `ActionMenu._input` does and drive
`find_valid_focus_neighbor(SIDE_*)` + `grab_focus()` steps from a
`MenuRepeatPolicy("ui_left","ui_right","ui_up","ui_down")` poll — **vertical
only**: left/right must stay with the focused control (the Menu Scale HSlider
and OptionButtons consume them); or (b) explicitly re-scope GP-01's STATUS to
"Settings repeat deferred" so the rerun expectation and checklist row are
honest. (a) is small and reuses the tested policy; recommended.

## F3 (MEDIUM, feel) - Fresh-direction immediate fire means a menu opened under a held stick steps on its first frame

`MenuRepeatPolicy.poll()` fires immediately on any direction change from ZERO
(`scripts/shared/MenuRepeatPolicy.gd:60-63`). `clear()` resets `_held_dir` to
ZERO — so a stick **still held from before the menu opened** reads as a fresh
direction on the very next poll and steps focus instantly. The comment at
`ActionMenu.gd:157-159` ("doesn't carry a stale step into the fresh menu")
claims the opposite of what clear() does here: it converts the stale hold into
an immediate step.

Concrete repro: hold stick-down to run the map cursor onto a unit, press A
while still holding — ActionMenu opens and instantly hops focus off the
default action. The old per-event code required a *new press*, so this is a
small regression in exactly the "cadence feel" area the rerun judges. Same
applies to `UnitDetailsScreen.open()`.

**Recommendation:** add a wait-for-neutral latch — after `clear()`, `poll()`
returns ZERO until it has observed the direction at ZERO once, then fresh
directions fire immediately as today. One flag in MenuRepeatPolicy, one new
`test_menu_repeat_policy.gd` case ("held direction across clear() does not
step until released"). Footnote, same file: on a perfect diagonal the dominant-
axis tiebreak picks horizontal, which ActionMenu ignores — a held up-diagonal
never steps. Harmless for v1; noting so it isn't rediscovered.

## F4 (LOW) - Brand-correct words stop at buttons; trigger-axis labels stay positional on a PS pad

Q2 chose brand-correct WORDS now. `joypad_button_label()` handles faces +
PS shoulders (L1/R1), and rebind rows brand through `_binding_label_for_row`
(`SettingsScreen.gd:983`) — but that helper only brands
`InputEventJoypadButton`. Axis bindings fall through to
`_joypad_axis_to_string` (`scripts/shared/InputDisplay.gd:269-280`), which has
no brand parameter and always prints "LT"/"RT" — wrong words on a PlayStation
pad (L2/R2), and zoom (the binding the tester actually fought with and
rebound) is exactly a trigger axis. `first_pad_label_for_action(:159-161)`
has the same hole, so live prompts share it.

**Recommendation:** thread `brand` into `_joypad_axis_to_string` (PLAYSTATION
→ L2/R2; sticks are brand-neutral) and use it from both call sites. A few
lines + one `test_input_display.gd` assertion; ride it with F2 rather than
holding the rerun for it.

## F5 (NOTE) - Polled menu input bypasses handledness; a registered caveat for future overlays

`Input.get_vector` reads device state directly, so the `_process` pollers in
ActionMenu/UnitDetailsScreen step regardless of who consumed the events. Today
that's safe (nothing stacks on either while both accept input; MapCursor is
suppressed/non-FREE under menus), but any FUTURE overlay that opens on top of
these while leaving them visible will double-step underneath — and the event
consumption in their `_input` won't save it, because the poller doesn't look
at events. Not a defect to fix now; worth a line in the B6-INPUT focus-seam
notes so the next modal author inherits the constraint deliberately (the
`SelectionCursor`/`ModalScreen` seam is the eventual owner).
