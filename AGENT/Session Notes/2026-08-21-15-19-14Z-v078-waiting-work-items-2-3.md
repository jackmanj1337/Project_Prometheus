## What was done

### Item 2 — `REQ-LEGACY-REGISTRY-RECONCILE-2026-08-20`, closed

**The row's premise was imprecise, and correcting it decided the outcome.** The row is
titled "two formula evaluators shipped" and asks whether the legacy one has a surviving
obligation. It does not — but not for the reason the row implies. The two classes are not
two evaluators of the same thing:

- `FormulaEvaluator` is a **numeric value-term** evaluator: fixed-point `add`/`sub`/`mul`/
  `div`/`pow` over `source_id` lookups.
- `RequirementFormulaRegistry` composed **booleans** into `{met, reason}`.

Its real successor is `RequirementSystem`, which meets the obligation more strongly on
every axis:

| Legacy | Successor |
|---|---|
| `always` | **Deliberately not carried.** It was a fail-**open** leaf, and `validate()` now rejects an empty composition precisely so a malformed tree cannot open a gate. Re-adding it restores the shape. |
| `fact_equals` | `flag` / `campaign_var` predicates, plus `compare` over full value terms rather than a flat `==` on a facts dictionary |
| `all` | `op` `all`/`any`/`not`, with per-child reason collection |
| `MAX_DEPTH 8` | pack-lowerable depth and node budgets under a 32/512 ceiling |
| raw `reason` string | structured `{text_key, params, predicate_path, gate}` rendered via `TextDB` — localizable, where the legacy string was not |

**Coverage retired by citation rather than rewritten.** The row asked for the assertions to
be retired, not deleted. The single assertion is already covered — and covered more
thoroughly — by `test_requirement.gd:39` ("structured unmet reason") and `:44` ("text-key
reason rendering"). That file is a **claimed path of `UNMET-REASON-TEXT-TABLE-2026-08-20`**,
which is `in_review` and is §3 of the checklist in the tester's hands, so it was cited
rather than edited. A comment at the deletion site records where the coverage went, so it
does not read as a dropped assertion later. `FormulaResult` was kept — hit, range and cost
registries all return it.

**One obligation is genuinely not carried**, and is recorded rather than fixed:
`PREDICATE-PARAM-VALIDATION-2026-08-21`. Legacy `fact_equals` rejected unknown parameters;
`RequirementSystem.validate()` has no generic per-predicate parameter validation — only
`presentation.gate`, composition children, and `compare`'s value terms. So
`{predicate_id: "has_item", params: {itemid: "iron_sword"}}` validates clean and evaluates
against a missing key. The failure direction is what makes it worth a row: predicates read
params via `.get()` with defaults, so a typo does not throw — it silently yields
`met=false`, failing **closed**. Safer than opening a gate, but undiagnosable from the
player side and invisible to the author. Blocked on the same `in_review` row, since the fix
edits `RequirementSystem.gd`.

### Item 3 — `PACK-SCHEMA-FRESHNESS-CHECK-2026-08-21`, built

**The row's proposed shape was rejected on evidence.** It named
`scripts/tests/test_pack_schema_freshness.gd`. But `run_tests.sh` runs in CI, and this
repo's CI checks out **only this repo** (`actions/checkout@v4`, single repository), so such
a suite would find no packs and pass green on every CI run — a suite that checks nothing,
which is the exact failure mode being fixed. The handoff flagged this asymmetry as "the
whole design problem" and it turned out to be decisive.

Built instead as `scripts/ci/check_pack_freshness.sh`, wired into **pre-push** — the one
place both the engine schema and the sibling pack repos are visible, and the moment a
schema change is about to be published. Measured cost: **0.69s per pack**, so the
performance objection to binding it there does not survive measurement. Where it cannot run
it says so **loudly** and exits 0, naming the coverage it is not providing.

Three independent failure signals, because the tool exiting 0 is not by itself evidence:
non-zero exit, absence of `adapter valid: true` in the output, and a validates-but-loads-
nothing counts line — the exact shape the broken packs had.

**Verified in both directions.** Against the real workspace it finds and passes 2 packs.
Against a deliberately broken probe (a pack skill file deleted while the catalogue still
referenced it) it exits 1 and names the cause. The probe was removed afterwards.

**Both current packs are green**, checked before designing anything: Pack_0 and Pack_FE
proving grounds both report `adapter valid: true`, 8/8 playable maps. So this ships as a
regression guard, not a repair.

**Two bugs the both-directions verification caught**, either of which a green-only run
would have shipped:

1. The sibling glob used the wrong `find` depth (`manifest.json` is at depth 4, not 3) and
   reported **SKIPPED against a workspace that had both packs cloned** — the check
   demonstrating its own worst failure mode.
2. The failure diagnostic grepped for expected phrasings and so reported a failure
   **without ever printing what broke**; the error detail is a free-form indented line.
