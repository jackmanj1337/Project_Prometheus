**Must-do 3 — mobile/web, three of the four UX gaps.** Touch was unavailable *by
construction* on the one platform the bundle exists to test: Godot tags `mobile` only
for a native export, so a PWA on a phone reported no touch capability; `web_ios` /
`web_android` now identify it and seed the platform default. Safe-area insets were
zero because `DisplayServerWeb` implements none; the shell now publishes the canvas
rectangle alongside `env(safe-area-inset-*)`, and window-pixels-per-CSS-pixel is
**measured** from that rectangle rather than taken from `devicePixelRatio` — whether
the backing buffer is CSS×DPR depends on the export's hidpi handling, so trusting DPR
would be a guess that mis-sizes every inset. The default UI scale came from the wrong
measurement: the identity diagonal is screen-derived and calibrated for a desktop
monitor, and on a phone canvas it picks the 0.5 minimum, which *is* the reported "text
is physically small"; a mobile browser now fits the largest 0.5 step that still holds
the 1280×720 design floor inside the actual canvas, snapped down.

**Portrait was deliberately not attempted**, and not for lack of time. In portrait the
binding constraint is width: 1179 backing pixels cannot show 1280 logical pixels at
any factor ≥ 1, so the fit lands at the 0.5 minimum whatever the default says. No
settings value fixes portrait. It needs the Game View viewport editor (controller
Slice 3), which is what lets the canvas occupy part of the screen instead of all of
it. The CSS rotate-notice stopgap stays, and its comment still names the row.

### Browser verification (added later the same session)

The headless claims above were then checked against a real v0.7.0 web export of the
candidate, driven with Playwright/Chromium on loopback. The probe reads engine state
through the test bridge (`scales.content`, `scales.safe`, `viewport`) rather than
through the JavaScript under test. `web_ios` is decided in `godot.js` purely by
`ua.indexOf('iPhone')`, so a user-agent override exercises the real mobile branch.

- Desktop 1280×720: main menu, content 1.0, zero insets — no regression.
- iPhone-emulated landscape (852×393 CSS, DPR 3 → 2556×1179 backing): content **1.5**,
  viewport 1704×786, no page errors. Exactly what the unit test predicts, and clear of
  the design floor.
- Safe-area feed: CSS insets of 47/21 arrived as engine insets 94/42 — 47 × (2553/851
  measured ratio) ÷ 1.5 content scale. Both conversions proven by those numbers.
- The exporter baked `version=0.7.0`, so the §4 bump reaches the BUILD STAMP.

**The run found a defect that is older and wider than this work.** `load_settings()`
returns early when there is no settings.cfg, and the derived content-scale default
lived only in the branch that reads an existing file *missing the key* — an upgrade.
So the identity-diagonal default reached upgrading players and never reached a new one,
on any platform. It survived because everyone testing already has a cfg. Fixed, and the
regression test overrides the derivation with a sentinel because headless derives 1.0,
which is indistinguishable from the literal default; it was confirmed to fail against
the old code.

**Still unverified: real WebKit hardware.** Chromium with an iPhone user-agent proves
the branch and the arithmetic. It does not prove physical safe areas, notch behaviour,
or legibility.
