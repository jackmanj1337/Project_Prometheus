## 1. The three questions, answered
- **History storage** — already designed, **two levels**: transient **resume** = the `[DLG-11]`
  `visited_trail` (ordered entry ids shown = the branch taken); persistent **memory** = `choice`
  `set_flag` → `[F6]` + the `conversations_seen` latch. No transcript blob.
- **Branch authoring** — `[DLG-2]`/`[DLG-5]`: labeled **segments** + `choice` options that `goto`
  labels; the `[DLG-8]` editor visualizes it.
- **Conditional availability** — the new part; **low-to-moderate difficulty** because the branching
  machinery exists and every predicate is a ~1-line read over an existing accessor.

## 2. The insight → foundation F16
The listed conditions are the **same predicate set** MET (`[MET-4]`), `[VIL-6]` tile-action
requirements, `[RCR-4]` recruit eligibility, `[IEQ]` `req_flags`, and objectives all want. So **one
shared author-extensible Requirement system**, not a dialogue-local language. **Net-simplifying** —
replaces scattered ad-hoc condition code with one evaluator + one display path.

**Owner calls (2026-06-25r):** shared foundation (not local) · subject = **author's choice** (both
participant-relative AND named/party) · granularity = **option + segment + whole conversation** ·
gated-out UX = **author's choice per option** (hidden | shown-disabled-with-requirement, the
`[VIL-6]`/`[VIL-7]` model).

## 3. `[REQ-1..8]` (F16)
- **REQ-1** one shared `Requirement` = an `all/any/not` tree of typed predicates (consumers: dialogue,
  MET, VIL-6, RCR-4, req_flags, objectives).
- **REQ-2** v1 predicate vocabulary, each a thin adapter: `flag` (F6) · `unit_is/present` ·
  `class_level` (`UnitData.level`) · `proficiency` (`weapon_rank_for_wexp`) · `stat`
  (`get_effective_stat`, string-keyed → F14 too) · `has_skill/trait` (`UnitData.skills`) · `has_item`
  (`{location: held|equipped|convoy}` over inventory + `[CNV]`). Author-extensible via the F4
  profile-style registry.
- **REQ-3** per-predicate **subject selector**: `speaker | participant:<role> | unit:<id> | active_unit
  | party(any|all)`.
- **REQ-4** AND/OR/NOT tree (objective-group precedent). **REQ-5** renders to text (per-type F13
  templates) for "[Requires: X]" + shown-disabled UX. **REQ-6** boundaries: F6 flags = one source; F5
  status = effects (queryable via `has_condition`, not owned); relationship matrix = separate axis.
  **REQ-7** F1: authoring data; reads reserved state; **no new save surface**. **REQ-8** generalizes
  MET-4 / VIL-6 / RCR-4 / req_flags non-breakingly (consumers adopt, not relitigated).

## 4. `[DLG-14]` — dialogue consumes F16

option = per-option `hidden` (secret) | `shown_disabled` (rendered requirement).
