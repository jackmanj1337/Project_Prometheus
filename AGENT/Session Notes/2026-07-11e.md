# Session 2026-07-11e - Resolve V027-05a: MainMenu exempt from Menu Scale

Branch: `agent/claude/2026-07-11/ui-theme-rollout` (same playtest branch as 2026-07-11d).
User asked directly to resolve the `V027-05a` open decision left flagged at the end of
that session: exempt Main Menu from the shared Menu Scale setting and have it sit at
the maximum size the screen allows.

## What was done

- **Added `MenuScale.apply_to_fit_rect(target, available, min_factor=0.5,
  max_factor=3.0)`** (`scripts/ui/MenuScale.gd`) — a new general-purpose primitive
  that grows OR shrinks a grow-to-content panel to the largest size that fits a
  caller-supplied `Rect2`, then centers it within that rect (not necessarily the
  full viewport). This is a genuinely new capability: `apply_to()`/
  `_clamp_to_viewport` only ever shrink a requested factor down toward a fit,
  never grow it, and always measure against the full viewport. Refactored
  `_clamp_to_viewport` to share the new `_fit_factor()` helper instead of
  duplicating the ratio math.
  - **Empirically discovered the fit isn't perfectly proportional to factor**:
    default_font_size and container separation scale with factor, but a
    Button's own StyleBox padding (baked into the engine default theme, since
    these targets carry no custom Theme) does not — it's a fixed additive term.
    A single proportional estimate from the factor-1 baseline systematically
    undershot the true fit (verified: a naive one-shot estimate landed at
    (158,305) against a genuinely achievable (199,389) for the same available
    rect). Fixed by iterating the estimate up to 5 times, each pass re-deriving
    from the PREVIOUS pass's actual measured size rather than the original
    baseline — converges to within a couple pixels in practice (confirmed via
    an ad-hoc diagnostic script, not committed).
  - The final pass is an unconditional (not `min_factor`-bounded) shrink-only
    safety clamp, so a pathologically small `available` rect can never leave the
    result overflowing its bounds — staying inside the caller's rect always wins
    over the `min_factor` readability floor. (A truly degenerate rect smaller
    than the content's fixed-padding floor can still show minor residual
    overflow — mathematically no factor fits it — but that's far below any
    realistic window size for MainMenu's four buttons.)

- **`MainMenu.gd`**: `apply_menu_scale(_factor)` now ignores the incoming factor
  entirely and calls `MenuScale.apply_to_fit_rect($Panel, _available_rect())`.
  `_available_rect()` computes the vertical band between `TitleLabel`'s bottom
  edge and `VersionLabel`'s top edge (both fixed-position siblings, each inset
  by a 24px `_AVAILABLE_MARGIN`), so the panel can never grow into either — this
  is exactly the shape `V030-REG-01` (Continue overlapping the title at 2.0x)
  had, now prevented by construction rather than by a fixed size cap. MainMenu
  stays in the `menu_scale_targets` group solely to keep receiving
  SettingsManager's existing debounced resize-refresh `call_group`, not because
  it follows the shared setting — documented inline since that's a non-obvious
  reason to stay in a group whose name says "scale target."
  - Confirmed at native 1280×720: Panel grows from its old fixed 300×210
    authored footprint to a content-driven fit that uses 389 of 392 available
    vertical pixels (99%) without touching either label.

- **New permanent test coverage** (not just the throwaway ad-hoc scripts used to
  investigate the nonlinearity above):
  - `test_menu_scale.gd`: new `_check_fit_to_rect()` — grows a synthetic
    3-button panel into a generous rect (confirms real growth + stays in
    bounds) and shrinks it into a realistic tight rect (confirms no overflow).
  - `test_main_menu.gd`: three new assertions — `apply_menu_scale(2.0)` doesn't
    change the panel's fitted size (factor genuinely ignored), the panel never
    intersects `TitleLabel` or `VersionLabel`, and the panel grew past the old
    fixed 210px height.
