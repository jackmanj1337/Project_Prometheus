## What was done

Continuation of [2026-08-01-23-30-00Z-crossing-resolver](2026-08-01-23-30-00Z-crossing-resolver.md).
Built **Band 6 fog slices 1 and 3**, which gives the crossing resolver its first
real consumer and proves the seam carries a feature end to end.

**Slice 1 — `FogService`.** One `compute_visible_tiles(faction, …)` seam
returning the union of each living faction unit's flat Manhattan
`line_of_sight` disc (`[FOW-1]` A, `[FOW-6]` A). Manhattan specifically, matching
`GridManager._tiles_in_range`, so vision reads with the same ruler as weapon
range instead of introducing a second notion of "within N tiles". The set is a
Dictionary-as-set so the render mask and the per-step check are both O(1)
lookups, and it is bounds-clamped so the mask's complement can never punch a hole
in nothing.

**Deviation from the plan, deliberate:** `fog_enabled` landed on
**`BattleEncounterDef`**, not `MapData`. The plan (2026-07-03) said "next to
`enemy_placements`" — but the encounter/map split happened after it was written
and took `enemy_placements` with it, so the encounter layer *is* the plan's
intent today. `MapData.fog_enabled` survives only as a legacy authoring shim that
`ResolvedBattleData.from_legacy` forwards. The plan now records this.

**Slice 3 — `FogRuntime`, the first crossing consumer.** The ambush is a
registered trigger `{interrupt: halt, ends_activation: false}`. It does **not**
touch `move_along_path`; the plan's step 1 ("in the per-step tween loop") is
superseded by `[PCM-3]` and was not followed. The payoff is concrete: fog gets
Instant-speed and AI parity for free, and the suite asserts it.

The ambush check reduces to *"is there an undiscovered hostile within the mover's
vision radius of this tile"* — because only the **mover's** disc moves during a
move. Every other unit stands still, so anything they can see was already banked
at phase start. That is why there is no per-step full-union recompute.

**Slice 2 (render) is deliberately not built.** The fog mask overlay and enemy
hiding are a rendering change needing a Windows visual pass the container cannot
give, so per AGENTS.md they are split off rather than closed on a headless green
suite. A `fog_enabled` encounter today computes vision and halts moves correctly
but **draws no fog** — that is stated in `GDD_06`, the roadmap, and the plan, so
nobody mistakes it for finished.

**Two defects found and fixed while wiring it up:**

1. **The crossing consumer could outlive its map.** `CrossingService` is an
   autoload; a `FogRuntime` registered by `GameMap` would still be registered
   after the scene unloaded, leaving the next (probably non-fog) map with a probe
   bound to a freed object. `GameMap._exit_tree` now unregisters, and the
   resolver reports a dead probe once instead of erroring per crossed tile.
2. **Both new suites were partly testing nothing.** Adding a node named
   `CrossingService` under `/root` only wins the name race if it lands *before*
   autoloads attach on the first frame; after any `await`, Godot renames the
   newcomer and `Unit` resolves the real autoload. `test_crossing_resolver`
   happened to add its node pre-frame and passed honestly; the fog suite awaited
   first and silently exercised an empty resolver. Both now use the live
   autoloads via one `_autoload()` helper. Worth remembering: **a passing suite
   that adds a node named after an autoload is not evidence until you check which
   one the code under test resolved.**
