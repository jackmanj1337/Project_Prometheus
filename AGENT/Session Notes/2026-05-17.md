`.godot/global_script_class_cache.cfg` is only regenerated by the Godot **editor**;

edits that land in the extraction commits — the design's §7 clone/CI breakage risk is

### Step 5 — Fix the key-repeat double-`DELAY` quirk
The old `_process` re-armed the repeat timer with `KEY_REPEAT_DELAY` on the *first*
auto-repeat step (the `_held_initial` ternary read the flag before clearing it), so
the first repeat waited 0.25s instead of 0.10s. The design's "one-line fix" (clear
`_held_initial` before the read) would make the ternary always pick `RATE`, leaving
`_held_initial` a dead field — so the field was removed outright and `tick()` now
always re-arms with `KEY_REPEAT_RATE`. The press still waits `DELAY` (set by
`arm_repeat`), every repeat after waits `RATE`. `test_map_cursor_input.gd`'s quirk
test repointed to the fixed behavior.
- Commit: `Fix key-repeat double-DELAY quirk: first auto-repeat now uses RATE`

## Addendum — Future-Feature Discussion (post-Session-J, same day)

A planning-only discussion. **No code was changed — docs only.** Recorded in full so
the discussion can be resumed later.

### What was decided
- **Four-faction system** confirmed as the long-term plan: blue (player), green
  (AI ally), red (AI enemy), yellow (AI, hostile to all). Alliance groups
  `{blue,green} {red} {yellow}` — two units are hostile iff in different groups.
- Any **non-blue faction** may be assigned to a **hotseat slot** for human control;
  blue is always human (player 1).
- Turn order is **configurable per map, default `blue → green → red → yellow`**.
- Victory/defeat stays **blue-centric only** — other armies have no win state.
- AI is **faction-blind**: targets scored by HP / strength / terrain danger /
  objective-criticality, not by which army a unit belongs to.
- Factions are **data-driven** (not a code enum) so a 5th+ faction is near-free —
  pure data for an AI faction.
- Online play sequenced **hotseat → LAN → online**; recommended networking model is
  **host-authoritative** client-server.
