# Session 2026-07-11b - UI-INSPECTION headless preview harness + MenuScale theme-clobber bug

Branch: `v0.3.0-features`. Picked up the `UI-INSPECTION` track queued at the end of
2026-07-10's RESUME note: built the throwaway headless preview harness (option (c)
from that note), wired the Mana Soul theme into the two remaining draft-UI screens,
and — while building the harness — found a real, confirmed bug in `MenuScale.gd`
that the harness then verified directly.

## What was done

- **Wired `assets/themes/manasoul_ui.tres` into `UnitDetailsScreen.tscn` and
  `AttackPreview.tscn`** (`ActionMenu.tscn` already had it from 2026-07-10's
  `4d85bcb`). `AttackPreview`'s root `Control` had no theme before; added one.
  `UnitDetailsScreen`'s `Panel` had a hardcoded `StyleBoxFlat` (`bg_color =
  Color(0.12, 0.12, 0.16, 1)`) overriding any theme — removed it so the 9-slice
  panel style can reach the node. All four affected test suites
  (`test_action_menu`, `test_unit_details_screen`, `test_attack_preview_selector`,
  `test_attack_preview_position`) stayed green, and no assertions depended on the
  removed flat stylebox.

- **Built `scripts/tools/ui_inspection_preview.gd`** — a `SceneTree` tool script
  (`godot --headless --path . --script res://scripts/tools/ui_inspection_preview.gd`),
  not a test (no `scripts/tests/` entry, not part of `run_tests.sh`). Instantiates
  `ActionMenu` / `UnitDetailsScreen` / `AttackPreview` under an offscreen
  `SubViewport` with mock data (stub units/grid mirroring the existing
  `test_action_menu.gd` / `test_attack_preview_selector.gd` stub patterns), and
  runs two kinds of checks:
  - **Effective-theme resolution** — `node.get_theme_stylebox(name, type)` on the
    *live* node after `apply_menu_scale()`/`show_for()`/`open()` runs. This walks
    Godot's real ancestor-theme fallback chain, so it tells the truth about which
    StyleBox a node will actually render with, independent of GPU/pixel output.
    This is what caught the bug below.
  - **Layout sanity** — `Control.get_global_rect()` sibling-overlap (the shape of
    bug V030-REG-01 was) and viewport-bounds checks.
  - PNG capture is attempted too (`SubViewport.get_texture().get_image()`), but
    **this container's headless Godot has no working rendering driver** — `dummy/
    storage/texture_storage.h` in the error trace, and `get_image()` returns null
    every time. Confirms the 2026-07-10 RESUME note's caveat. The harness reports
    this as a WARN (not a FAIL) and keeps going; treat the Windows-host editor as
    the visual source of truth per `AGENTS.md`, same as always. The structural
    checks above don't need a GPU and are the load-bearing part of this tool in
    this container.
  - `SCALE_FACTORS` mirrors `SettingsManager.MENU_SCALE_LEVELS`
    (`[0.5, 0.75, 1.0, 1.25, 1.5, 1.75, 2.0]`), duplicated rather than imported
    since this tool never boots that autoload.
  - Output goes to `res://ui_previews/` (gitignored: `/ui_previews/` added to
    `.gitignore`, and the directory added to the `00_Master_Review_Procedure.md`
    §2 coverage map next to the existing `builds/` precedent, so `check_docs.py`
    check 11 doesn't flag it as an unowned top-level dir).

- **Found and confirmed a real bug: `MenuScale.apply_to()` discards custom
  themes.** `scripts/ui/MenuScale.gd:132-134`'s `_apply_type_scale()` does
  `target.theme = _scaled_theme(factor)`, where `_scaled_theme()` builds a
  **brand-new bare `Theme.new()`** (only `default_font_size` + container-spacing
  constants — see `MenuScale.gd:139-148`) and assigns it directly, with no merge
  against whatever theme was already on that node. Static reading flagged this
  before the harness ran; the harness then confirmed it empirically:
  - **`ActionMenu` — confirmed broken.** `ActionMenu._ready()` calls
    `MenuScale.apply_to(self, factor, false)` — `self` is the exact node
    `ActionMenu.tscn` sets `theme = manasoul_ui.tres` on. The harness's effective
    style check showed `PanelContainer/panel` and `Button/normal` both resolving
    to plain `StyleBoxFlat` (engine default) at **all seven** Menu Scale factors,
    including 1.0x. The 9-slice panel, custom buttons, and CC0 font measured on
    2026-07-10 (margins 20/14 panel, 14·4/12·7 button, font size 16) have never
    actually rendered in-game — every `ActionMenu.show_for()` call clobbers them.
  - **`UnitDetailsScreen` — confirmed NOT broken, for a specific structural
    reason.** Its `ModalScreen` base's `apply_menu_scale()` targets
    `_menu_scale_target()` = `get_node_or_null("Panel")`, a *child* of the themed
    root, not the root itself. Godot's theme lookup is a per-property ancestor
    fallback chain: `Panel`'s own (bare, scaled) theme doesn't define
    `PanelContainer/styles/panel`, so the lookup continues up to the root's
    `manasoul_ui.tres`, which does. The harness's effective-style check confirmed
    `PanelContainer/panel` resolves to the real `StyleBoxTexture` at all seven
    factors. (`default_font_size`/container spacing DO come from the bare scaled
    theme at each node it's assigned to — that's the intended scaling behavior,
    not a bug.)
  - **`AttackPreview` — theme correctly applied**, as expected: it extends plain
    `Control`, not `ModalScreen`, and has no `MenuScale` involvement at all.
  - **Root cause, in one line:** whether a screen's theme survives
    `MenuScale.apply_to()` today depends entirely on an accident of which node
    the theme happens to be assigned to relative to which node `MenuScale`
    targets — not on any deliberate design. `ActionMenu` and `UnitDetailsScreen`
    run through the exact same `MenuScale.gd` code path and get opposite results.
  - **Why this wasn't caught on 2026-07-10:** validation that session was headless
    only (no GPU, same limitation confirmed again this session), so the margins
    were flagged as "estimates" to verify visually later — but the real problem
    isn't pixel-accuracy of the margins, it's that the entire themed StyleBox
    never reaches `ActionMenu` at runtime regardless of margins. A pixel
    screenshot on the Windows host would have shown this immediately (default-gray
    buttons instead of the ornate 9-slice), which is presumably still worth doing
    to see it firsthand — but the effective-theme check gets there without needing
    a GPU at all.
  - **Not fixed this session** — the owner asked to build the harness first, i.e.
    to use it to confirm/visualize the bug before touching `MenuScale.gd` or
    `ActionMenu.gd`. Fix is scoped in the control-plane row (see below) but not
    started.

- **Secondary finding (lower confidence): `AttackPreview` panel overflow.** With
  real preview content and no `reposition()` call (the harness never wires
  `setup()`/a camera), the panel's authored anchor (`offset_top = 620` in a
  720px-tall viewport) plus its content-driven height overflows the bottom edge
  (`rect [P: (280, 620), S: (676, 230)]` exceeds the 720px viewport). This is
  flagged as a likely **harness-fidelity gap, not a confirmed production bug** —
  in real play `show_preview()` is always followed by `reposition()`
  (`_reposition_for`, `_hud_avoid_rects`, `_place_clear_of`), which repositions
  the panel relative to the units and screen edges. Worth a follow-up run with a
  stub camera/grid wired through `setup()` before treating this as a real defect.
