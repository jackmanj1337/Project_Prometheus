## What was done

Step 2 of the responsive redesign (`responsive_ui_redesign_2026-08-06.md`): the size-class
seam every screen conversion depends on. No screen was converted.

`ResponsiveLayout` (new autoload, registered after `SettingsManager`) derives a size class
from the logical viewport — `backing size ÷ content_scale_factor`, the factor being a
player-owned setting — as Compact (<600 logical px), Medium (600–1023) or Expanded (≥1024).
It carries the touch and controller density token sets that Menu Mode selects between, and
the Full / Standard / Minimal information-density token.

**The live behaviour is the substance.** The design flagged it as the part most likely to be
got wrong quietly, so three properties are implemented and tested rather than assumed:

- **Debounce (0.12s).** A window drag emits a resize per frame and a class change re-parents
  panes; a restarting one-shot timer makes a continuous drag publish once, when it stops.
  Same defect shape as the mobile controller's republish-during-gesture bug.
- **Hysteresis (24 logical px).** The rule is one sentence — widen the *current* class's band
  by the margin on both sides; if the width is still inside it, hold. Expressed that way it
  stays correct for a two-class jump (a maximise from 400 to 1600 lands on Expanded, not
  Medium) with no direction-of-travel special case.
- **Publish only on a real change.** This is the state-preservation mechanism. A screen that
  receives no signal cannot lose the player's selection, scroll position or open More Info
  target rebuilding for a change that did not happen.

**It does not touch `SettingsManager.gd`,** which `IMPL-FILEDIALOG-ESCAPE-TEXTINPUT-2026-07-29`
still claims. That file already emits `display_size_changed` at a settled point, and already
coalesces viewport resize, window resize *and* a `content_scale_factor` write (setting the
factor makes the Window emit `size_changed`). One upstream signal covers both inputs of the
model, so the seam consumes it and adds nothing. Menu Mode and information density are held
in memory until the claim clears and they can become persisted settings; the getters are
written so that wiring is a later change here, not a rewrite.

`UnitDetailsScreen`'s hard-coded `900.0` was the ad-hoc size class the design generalises, so
it now asks the seam and stacks below Expanded, and listens to `size_class_changed` instead of
the raw viewport signal.

**This moves a boundary and the move is deliberate:** 900–1023 logical px used to lay out side
by side and now stacks. Side by side only at Expanded — not from Medium as the target model
has it — because the scene's `Panel` still carries `custom_minimum_size` 760×540, so a Medium
viewport cannot honour the target layout until that minimum is fixed in the screen's own
conversion branch. Stacking is the direction that cannot push the panel wider than the window.
Restoring the band is a call for that conversion's visual pass, not something to revert blind.

Classification is `static` and side-effect free on purpose. Headless pins the logical viewport
at the project base 1280×720 (`SettingsManager._apply_content_scale` falls back to
`CONTENT_SCALE_ASPECT_KEEP` because a 64×64 headless window would make all layout maths
meaningless), so a headless test cannot vary the viewport. Direct calls are the only way these
rules get covered at all.
