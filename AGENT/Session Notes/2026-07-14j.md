  UI.** The roadmap gained a `B4-PREP-DEPLOYMENT` slice table (Slice 1
  Implemented; Slices 2-3 Planned).
  - **The load-bearing change: deployment stops being INFERRED and becomes a
    CHOICE.** `GameMap._spawn_units` derived the player's side from roster order
    truncated by the start-tile count — a fallback that merely *looked* like a
    decision. `GameState.next_map_deployment` (`unit_id` -> start tile) now
    stages the real one.
  - **An empty plan means "no prep screen ran", not "deploy nobody".** `GameMap`
    then keeps the historical roster-order rule, so the bare single-map launch —
    which has no campaign position at all — behaves exactly as it did before.
    Additive, as ever.
  - **`GameMap` revalidates before it spawns.** Prep will gate Begin Battle on a
    legal plan, so an illegal plan reaching the map means the party or the map
    changed underneath it: the launch fails loud rather than spawning a
    half-legal board (a fallen unit, two units stacked on one tile).
  - **The plan is not persisted, but it DOES survive a Retry.** A campaign save
    is parked between maps, so a reload lands back on prep and the player deploys
    again — same reasoning as the unpersisted pending result, and no new F1 save
    row is owed. Retry, though, reloads the map scene *without* reconfiguring the
    launch, so a replay redeploys the units the player actually chose instead of
    silently falling back to roster order.
  - `scripts/shared/DeploymentPlan.gd` is the validator, with two consumers: prep
    (to gate Begin Battle) and `GameMap` (to refuse an illegal plan). It carries
    **no `class_name`** — it is preloaded, like `GameState`'s helpers, which
    sidesteps the global-class-registry reimport gotcha entirely.
  - **The `[CST-5]` node constraints finally have a reader.**
    `required_units` / `excluded_units` / `deployment_cap` have been authored and
    validated on `CampaignNode` since `B1-CST` Slice 1 with no consumer; this is
    it, which is why no schema change was owed.
- **Decision (asked and settled this session): a fallen `required_unit` is
  EXCUSED, not a launch block.** Under permadeath a dead unit stays in the roster
  (spawn skips it), so a node can legitimately require a unit the player has lost.
  Blocking would *strand the campaign* — no legal plan for that node could ever
  exist again, and the player's only recovery would be an older save. Whether a
  key death should END the run is a campaign-rules question (permadeath
  game-over), not a prep-validation one. A required unit that was never in the
  party at all is a different thing — an authoring error — and still fails loud.
