## 4. Gamepad layer implementation plan (`858f742`, then corrected `6be62e2`)

First wrote the plan: audited all **19 input-map actions** against every non-test call site →
locked action map (direct / menu-only / contextual / excluded). Fits a standard controller
with **zero combos** (the pause menu absorbs the long tail). Resolved the focus-wiring
question *with evidence* — the UI is a **hybrid** model (custom menus consume `cursor_*` in
`_input` then `grab_focus`; activation + Settings sliders/OptionButtons depend on Godot
`ui_*`), so **bind the gamepad to BOTH `ui_*` built-ins and the custom actions** (necessary,
not redundant). `show_danger_zone` → R3, with a **contextual** twist the user added: general
R3 = faction-wide threat, R3-over-an-enemy = that enemy's range — which **depends on the
unbuilt UI/UX item "individual unit threat range"** (dependency edge recorded). Debug toggles
excluded (release blockers).

**Then the review/correction pass (user: "can we get better solutions by rebuilding existing
code?").** Reading `MapCursorInput` showed the plan's "thin data edit" premise was **wrong for
the map cursor**: `decode_key(event: InputEventKey)` is keyboard-typed (a d-pad
`InputEventJoypadButton` never reaches it) and the repeat model assumes press/release edges
(an analog stick has none). The bones were already right (`Intent` enum + `is_action_pressed`
are device-agnostic), so the fix is a **decoder rebuild**, scoped as (user pick = "A+B now,
C with V021-15"):

- **Rebuild A (required):** widen `decode_key(InputEventKey)` → `decode(InputEvent)` (d-pad
  for free) + left-stick `Input.get_vector` polling into the existing repeat timer.
- **Rebuild B (cheap win):** zoom from edge-triggered → polled `get_action_strength` = free
  held-repeat + proportional analog trigger zoom (fixes the trigger-held gap).
- **#3:** unify `confirm`/`cancel` with `ui_accept`/`ui_cancel` event lists (closes the
  coincidental-overlap).
- **Rebuild C (deferred to V021-15):** an input-context owner replacing the
  `_input_suppressed` bool + per-menu consume discipline, letting menus move to native focus.
  It subsumes the V021-15 arbiter, so it's one job — recorded in the V021-15 design.

Plan: `gamepad_layer_implementation_plan_2026-06-20.md` (4 slices, headless test plan, DoD).

## 5. Web shell input — RESOLVED (`4cacfc3`)

Re-decided the deferred question. Checking the code beat the original binary: **`mouse_cursor=
"click"` (V021-17, tested) + Godot's default `emulate_mouse_from_touch=true`** means a canvas
**tap already drives the cursor** (relocate-then-confirm) and Control buttons press on the
emulated click — so the core needs **no bespoke bridge and no gamepad-layer dependency**.
Decision (user pick = phased): **direct-touch/click-mode primary now** (+ a ~7-button HTML
strip for no-affordance actions: Back, Menu, More Info, Inspect, Danger, Zoom ±),
**virtual-gamepad as a later optional toggle** riding the gamepad layer. The Web build can
ship **right after v0.2.3** as originally sequenced — the "plan gamepad first" detour still
paid off (surfaced the decoder facts; clarified the Deck, not the web shell, is the
gamepad-validation vehicle). **Load-bearing risk:** smoke `emulate_mouse_from_touch` on real
iOS Safari Godot-Web first. Updated web handoff + web plan + input-mode design + GDD_10.
