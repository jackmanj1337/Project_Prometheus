Investigation done for the defect brief, on this branch at `bd6b5adb`:

- All five FileDialog nodes across `CampaignLibraryScreen.tscn`,
  `LoadGameScreen.tscn`, and `NewGameScreen.tscn` do carry
  `FileDialogInputGuard.gd`. A missing guard is not the cause.
- Measured on Godot 4.6.3 (not read from docs): once a `FileDialog` is inside
  the tree, `fd.get_viewport()` returns the FileDialog itself, and the filename
  `LineEdit`'s viewport is the same object. So the focus check at
  `scripts/ui/FileDialogInputGuard.gd:66` queries the correct viewport. That was
  the leading hypothesis and it is ruled out.
- `display/window/subwindows/embed_subwindows` is `true` and no native
  file-dialog setting is present, so the guard script is genuinely in the input
  path.
- `scripts/tests/test_settings_manager.gd:887` exercises first-Escape by calling
  `dialog._on_window_input(...)` directly, with a comment at line 886 explaining
  that a dispatched global Escape races other headless suites. The test proves
  the handler body works and cannot prove the handler is ever reached. That is
  why the suite stays green while Windows fails.
