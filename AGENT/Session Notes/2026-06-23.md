## 1. Question explored
"How hard to bundle art + item labels into separated campaign data (e.g. Iron Sword in one game,
Bronze Katana in another)?" — grounded in code first:
- Content is **id-keyed + resource-driven**: inventories hold `weapon_id`/`item_id`;
  `DataManager.get_weapon(id)`/`get_item(id)` resolve them; loaded from global `res://data/` dirs.
- **`display_name` already lives ON the `WeaponData`/`ItemData` resource** → relabeling is free
  (author an override `.tres`); no theming layer needed.
- **No item icon field exists today** (items are text-only) → item art is net-new.

## 2. Decision (owner, 2026-06-23)
Ship the **basic stuff as DEFAULT content**; the **GUI editor** + campaign designers **choose how
much to include or modify**. = the **base + per-campaign overlay** fork (over independent-per-campaign).
- **Three layers:** core defaults (`res://data/`) → **campaign package** (authored content + labels +
  art; the overlay) → per-playthrough **save** (state by id; binds to a campaign id). **Art lives in
  the package, never in the save.**
- **Mostly cheap** because of the id-keyed/resource model; the real work is campaign-overlay loading
  + the save↔campaign binding (both already in §2/DMR scope).

## 3. Sub-decisions flagged (recs, NOT yet ratified — for the I3 register/build)
include = inherit-all-then-add/override/**exclude**; override granularity = whole-resource-replace
-by-id v1; ids share the default namespace (validate collisions); pack records the default-content
version it overlays; `res://` (shipped) vs `user://` (GUI-authored).
