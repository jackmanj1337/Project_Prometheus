## 3. Input-mode architecture design — commit `dde2f88`

Long design conversation, forward-looking (no code). Wrote
`AGENT/Docs/input_mode_architecture_design_2026-06-20.md`. Key decisions reached:
- **Model input *modes*, not platforms.** Gamepad mode is the shared backbone of Steam
  Deck + phone-with-controller + the virtual-gamepad touch style + the debug-web shell;
  building it once unlocks all four. **Verified: zero gamepad bindings exist today** —
  the keystone dependency.
- **Setting vs active-mode split.** Setting = `Auto | Gamepad | Touch | Keyboard&Mouse`;
  active mode is derived at runtime.
- **Nested tree:** Virtual gamepad is a sub-option under **Touch**; `mouse_cursor`
  relocates under **Keyboard & Mouse**.
- **Detect-floor + conditional promotion** (user's idea, generalized): boot in detect,
  promote to the saved setting iff available; rule fires on every device connect/
  disconnect, not just boot. Cold-start uses a platform-seeded provisional mode.
- **Gray-don't-hide** unsupported modes **plus** a back-door fallback so a player who
  *arrives* at a dead mode (corrupt cfg, cloud sync, disconnect) is never trapped.
  Distinguish "unsupported" (touch on desktop → gray) from "absent" (gamepad, no
  controller → don't gray).
- **Dual focus/pointer UI tax** is the standing constraint on all new menus.
- Sequencing: gamepad layer → Steam Deck (eventual, lower priority than mobile) →
  virtual-gamepad + debug-web shell → touch-native. Open decisions listed in the doc.
