## 3. Issue 6 — Manual save: auto-generated id, no manual filename — *low-med risk*

Diagnosis confirmed: raw id at `PrepScreen.gd:218-228`; engine error on bad input at
`SaveManager.gd:86-92`; the scene exposes **two** fields incl. "Slot id" at
`scenes/ui/PrepScreen.tscn:80-89`.

**DECISION (maintainer, 2026-07-21) — drop the manual filename entirely.**
1. **UI:** remove the `SlotId` field. The player never types a filename, so the
   invalid-id path is unreachable from normal use (kills the bug + the log noise).
2. **Auto-generated slot id** = `<chapter/node-slug>-<activity>-<timestamp>`, e.g.
   `ch4-prep-<ts>` or `<chapterlabel>-post-<ts>`. Sources: the active campaign node
   (chapter) for the slug, the current activity (`prep` on the PrepScreen surface;
   `post` for a future post-battle save surface), and a timestamp with enough
   precision to be collision-free (fall back to a `-N` counter if two land in the
   same tick). The id is filename-safe by construction and human-readable for
   debugging (advances the human-readable-labels goal).
3. **Human label** derived from the same context (e.g. "Chapter 4 — Prep"), shown in
   the load list.
4. **Overwrite protection (the confirmation):** on save, if a save with the **same
   label** already exists, show a **confirmation dialog before overwriting it**
   (confirm → delete the prior same-label slot and write the new one with a fresh
   id/timestamp; cancel → abort). This bounds accumulation to one save *per label*
   instead of endless timestamped files — resolving the "endless slots" risk without
   silent clobbering.
5. **SaveManager:** since ids are now always engine-generated and valid,
   `is_valid_slot_id` becomes an internal invariant — **keep `push_error` there** (a
   bad *generated* id is a real internal-contract violation, not user input). No
   user-facing rejection path remains.

**Open sub-decision (settle at implementation, does not block):** is the human label
**fully auto-derived** from context, or **optionally player-editable** (auto-filled,
editable before confirm)? Auto is simpler; editable lets the player name a save.

**Tests:** id generation is filename-safe + unique (same-tick collision falls back to
`-N`); saving with an existing label triggers the overwrite confirm and, on confirm,
replaces exactly that slot (count unchanged); on cancel, nothing is written; **no
`push_error`** on any normal manual save. Existing saves stay compatible (`save_label`
and slot ids are already independent).

## 5. Issue 5 — `x` closes the Import field — *REWRITE (Codex: WRONG as first drafted)*

**[rev] The suppression the plan proposed already exists** and still fails:
`SettingsManager._input` (`:191-226`) intercepts printable `confirm`/`cancel`/`ui_cancel`
for a focused `LineEdit`/`TextEdit` so text editors get first ownership; there is a test
(`test_settings_manager.gd:836-856`) — but it drives `_input()` directly on a root
`LineEdit`, **not a real FileDialog**. So re-adding suppression repeats the failed fix.

**Root-cause hypothesis to confirm first:** a `FileDialog`'s filename editor lives in a
separate `Window`/viewport, so `SettingsManager.get_viewport().gui_get_focus_owner()`
does not see it, and the mirrored `ui_cancel` still closes the dialog.

**Fix:** reproduce with an actual `FileDialog` receiving a **dispatched** key event;
then guard at the **dialog/owning-window** level (or suppress the mirrored `ui_cancel`
while a `FileDialog` is visible), not at `InputModeManager` (which is not the
arbitration owner). Keep `z`/`x` global; Escape exits the text box.

**Tests:** real FileDialog input at **all three** call sites; lower/upper X/Z, WASD,
selection replacement, key repeat, Escape.

## 8. Issue 3c — Manual end-turn Waits in roster order — *med risk, REWRITE (Codex: WRONG)*

**[rev] The naive loop does not produce N history entries.** `_queue_activation_history_push`
(`TurnManager.gd:674-706`) stores **one** pending metadata dict and coalesces all
same-frame calls into a single deferred `_flush_activation_history` (`:709-722`); it can
also auto-end the phase mid-batch; and `commit_action_event` only advances RNG, it does
not lodge history (`:861-870`).

**Fix — one TurnManager transaction** `commit_remaining_waits(faction_id, ordered_units)`:
1. suppress auto-end for the batch;
2. per unit, in order: commit the Wait RNG event → mark DONE → **flush one snapshot
   immediately** (bypass the same-frame coalescer);
3. request phase end only after the final snapshot.

Then `MapCursor._on_end_turn_requested` (confirmed branch) calls it with the active
faction's READY units. **[rev] Define roster order for non-blue controlled factions** —
`GameState.player_roster` only naturally orders blue; pick a deterministic order for
others.

**Tests:** N>1 produces N ordered entries; mixed READY/MOVED/DONE; paired/off-map units;
auto-end-enabled setting; hotseat factions; **deterministic RNG/history hash** across
runs; units READY again next phase.

## 9. Issue 4 — Modal rewind selector — *med-high risk, RISK (reuse existing lock)*

Diagnosis confirmed: MapMenu owns no lock and leaves its buttons active
(`MapMenu.gd:57-70,100-146`); the selector is a plain `Control` with minimal cancel
handling (`RewindSelector.gd:1-43`).

**Fix [rev] — reuse the existing EventBus refcounted lock; do NOT add a second counter.**
- `EventBus` already provides a **reference-counted** `acquire_gameplay_modal(owner)` /
  release (`EventBus.gd:61-98`); `GameOverScreen` already holds it for its whole visible
  lifetime (`GameOverScreen.gd:124-128,311-326`). Make **MapMenu an owner** of that same
  lock, with **idempotent** acquire/release on **every exit path and `_exit_tree`** (no
  leaked locks).
- Give hosts explicit `open_rewind_selector()` / `close_rewind_selector()` that
  hide/disable and later restore their **own** panel while the selector is up, and reset
  the selector's visibility on menu teardown.
- Note: extending `ModalScreen` alone does **not** acquire the gameplay lock
  (`ModalScreen.gd:331-348` is focus/cancel only) — it's a complement, not the fix.

**Tests:** Settings-over-selector transitions; menu teardown; rewind success/reload;
cancel; **node destruction leaves no leaked lock**; focus stays in the selector; closing
returns focus to the opener.

2. `CampaignManager._record_result` (`:517-529`): add **distinct `push_warning`s** for
   inactive-campaign vs active-campaign-with-empty-`_active_node_id`, so a dropped result
   is visible.
3. **Full-flow reproduction is mandatory** before any semantic change: launch
   `node_04_escape` via `CampaignManager`, pair via `MapCursor`, escape, await a frame,
   assert one successor option + no error; repeat separate; assert the support roster
   tile (also covers Issue 9). Do not touch branch/deployment logic until a failure
