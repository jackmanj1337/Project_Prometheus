# Web app — start here

The web build is **not** in this bundle, and that is deliberate.

`FREEZE-WEB-DISTRIBUTION-2026-07-26` forbids distributing any web build until the
content-extraction work completes. Shipping the web export inside a bundle that gets
unzipped onto a machine and served is distribution. So this document tells you how to
run it from the repository instead.

## Why the web items matter enough to bother

The PWA items — install to home screen, service worker, offline relaunch, durable
saves — are the ones a container cannot fake, and they are what
`IOS-DEVICE-PWA-VERIFICATION-2026-08-03` and `DEDICATED-TOUCH-CONTROLS-2026-08-03` are
waiting on.

## Run it

From the workspace, on the machine that has the repository:

```bash
scripts/export-web.sh --repo Project_Prometheus --mode release --build-type release \
  --build-stamp "v0.7.0 <commit>"
```

Then serve `builds/web/Project_Prometheus` and open it. Two ways:

- **Local loopback** — fine for a quick look on the same machine.
- **Tailnet host** — needed to reach it from your phone.

## HTTPS is not optional for the PWA items

A plain-HTTP page that renders proves **nothing** about installation, service workers,
offline launch, or durable storage. Browsers gate all four on a secure context. If you
open the page over `http://` on your phone, you can check layout and touch input and
nothing else — do not mark the PWA items either way from that.

Over HTTPS, the four checks are:

1. **Install** — the browser offers "Add to Home Screen"; the installed icon launches
   without browser chrome.
2. **Service worker** — reload with the network off; the page still loads.
3. **Offline relaunch** — close it fully, go offline, launch from the home-screen
   icon.
4. **Durable saves** — save in-game, force-quit, relaunch, continue.

## Saves live in browser storage

Not on the filesystem. Clearing site data deletes them, and so does an aggressive
"free up space" pass by the OS. The **export path is the only way to keep a save**, so
exercise it: export a save, clear site data, re-import it.

## Touch, safe areas and scale

Touch mode is chosen from the user agent (`web_ios` / `web_android`), and the safe-area
insets are measured from the published canvas rectangle rather than derived from
`devicePixelRatio`. On an iPhone in landscape the content scale should resolve to
**1.5** on a 1704×786 logical canvas.

Rotate to portrait and you should get a rotate notice rather than a squashed board.
That is a known limitation with a measured cause, not a bug: 1179 backing pixels
cannot show 1280 logical pixels at any factor ≥ 1. Confirm the notice appears; do not
report portrait layout itself.
