# v0.7.6 Campaign Library, Transfer I/O, and Direct Save Migration Plan

## Outcome

v0.7.6 repairs the failed v0.7.5 player journey. Importing a valid campaign pack immediately makes
its campaigns available in New Game; every installed version remains visible; native and web file
transfer use platform-owned pickers/downloads without a competing filename editor; and v1 gains a
bounded, safe direct save-migration seam. The editor shell now exists in the current integration;
this plan records its remaining device-access and acceptance contract. The accepted navigation target
remains current: Main Menu exposes Continue, Manage Library, Settings, and Quit; New Game and Load
Game are actions inside Manage Library.

The v0.7.5 return is rejected for release because a pack installed but New Game remained unreachable,
and the nested game filename/FileDialog surfaces disagreed about focus and input ownership.

## Fixed contracts

1. **Installed means playable/available, not simultaneously loaded.** Every admitted installed pack
   contributes campaigns to New Game. Runtime still activates one exact package id/version when a
   campaign starts.
2. **Player-library import requires playable content.** A pack with zero non-development playable
   campaigns fails preflight and is not promoted into the installed store. Editor working copies use
   a separate development workflow.
3. **Versions coexist visibly.** Campaigns from every installed version are listed side-by-side and
   matching names carry version labels. There is no implicit newest-version replacement or hiding.
4. **Platform owns external-file chrome.** Native desktop uses the OS dialog; Web/PWA uses browser
   picker/download. The accepted artifact suffixes are `<package-id>-<version>.clean-pack.zip`,
   `<package-id>-<version>.with-runs.zip`, `<package-id>-<version>.portable-run.zip`, and
   `<package-id>-<version>.status-record.json`. No game-owned filename modal
   precedes either. Cancel writes nothing and restores caller focus.
5. **Migration is opt-in, declarative, and copy-on-write.** v1 supports a complete deterministic
   same-package-id chain of allow-listed source-to-destination edges. The schema reserves arbitrary
   source package ids for a future policy expansion, but v1 rejects them.
6. **Future editor access is universal.** Readiness warnings must
   never disable or hide it. v0.7.6 does not build an editor entry or its warning.

## Immediate implementation slices

### Slice 1 — close the import/New Game deadlock

Files expected:

- `scripts/resources/CampaignArchivePreflight.gd`
- `scripts/resources/CampaignPackInstaller.gd`
- `scripts/resources/CampaignPackRegistry.gd`
- `scripts/ui/CampaignLibraryScreen.gd`
- `scripts/ui/MainMenu.gd`
- `scripts/ui/NewGameScreen.gd`
- focused campaign-library, zero-content, and New Game tests

Work:

1. Add one registry/preflight predicate for a playable campaign: non-development, structurally valid,
   resolvable starting node/map, and valid required runtime references. Reuse Tier-2 validation; do not
   create a weaker second definition.
2. Run the predicate during read-only preflight and again immediately before atomic promote. Return a
   stable `no_playable_campaign` diagnostic and leave both source archive and installed store intact.
3. Change the Main Menu New Game gate from active `DataManager` content to the installed registry's
   validated playable-campaign count.
4. On `CampaignLibraryScreen.campaigns_changed`, refresh the main-menu gate immediately. Do not load
   pack data merely to enable a button.
5. Populate New Game from all valid installed package versions. Label duplicate campaign presentations
   with version numbers and retain package id/version in every row.
6. On Start, transactionally activate the selected row's exact package id/version, then launch. A
   failed activation shows the existing player-facing diagnostic and preserves prior active content.

Acceptance:

- clean user data → New Game disabled, Campaign Library enabled;
- import returned replacement pack → New Game enables without restart;
- imported campaign is listed and launches its first map;
- two versions of one pack appear side-by-side and each activates its exact version;
- a zero-playable/dev-only pack is rejected before install;
- failed import or activation does not disturb the previously active package.

### Slice 2 — replace the custom filename/FileDialog hybrid

Files expected:

- `scripts/resources/TransferFileService.gd`
- `scripts/ui/FileDialogInputGuard.gd` (retire external-file text interception; delete if no callers remain)
- Campaign Library and portable-save transfer callers
- native/web transfer tests and browser harness coverage

Work:

1. Define semantic `request_open` and `request_save` backends returning bytes/result or cancellation;
   game systems must not depend on platform paths where Web cannot provide them.
2. Native backend uses Godot's native file-dialog support for filename, directory, overwrite, and
   cancellation. Pass the deterministic suggested name into that one dialog.
3. Web import uses the supported browser upload callback and Web export uses browser download with the
   same suggested name.
4. Remove the game-owned filename step and all picker-field interception from external transfers.
   `TextEntryService` remains for game/editor fields.
5. Make cancellation a normal result: no error popup, no output file, one focus restoration.
6. Audit `TextEntryService.begin/_prepare_host/_reset` independently so repeated sessions cannot leave
   duplicate `focus_exited` or `gui_focus_changed` connections. Add idempotent connection guards even
   after the picker trigger is removed.

Acceptance:

- Windows import and export use one platform dialog each;
- suggested export name is editable in the OS dialog;
- Web upload/download round-trip remains byte-valid;
- Escape/cancel closes only the platform picker and returns to the invoking button;
- cancel creates or overwrites nothing;
- logs contain no duplicate-signal connection errors;
- keyboard/controller navigation in game UI resumes after picker closure.

### Slice 3 — bounded direct save migration

Files expected after a source inventory:

- pack manifest/catalogue migration declaration resource and validators
- `SaveData`/`SaveManager` migration preview and transaction boundary
- reference-walking helpers owned by the save schema manifest
- Load/Campaign Library migration UI and focused fixtures

Minimum v1 declaration:

```json
{
  "source_package_id": "pack-id",
  "source_package_version": "1.0.0",
  "destination_package_version": "1.1.0",
  "aliases": {
    "campaign": {},
    "campaign_node": {},
    "map": {},
    "unit": {},
    "item": {},
    "class": {},
    "skill": {}
  }
}
```

Exact field names remain subject to the source inventory; they must follow existing catalogue/schema
conventions and open registries rather than introduce a closed migration type switch.

Work:

1. Inventory every persisted content reference and map each to its schema owner. Missing reference
   classes block implementation until added to the manifest.
2. Validate declaration identity, unique alias sources/destinations, destination existence, and lack of
   ambiguity. v1 requires source package id == destination package id and one direct edge.
3. Preview migration without mutation. Report pass-through references, mappings, and blockers.
4. Deep-copy/import the source save, apply aliases through registered reference walkers, set destination
   identity, and run full structural plus destination-content validation.
5. Commit as a new imported save only after validation succeeds. Never overwrite or delete the source.
6. Expose explicit Migrate/Import into Version action only when the destination declares that exact
   source. Unsupported moves remain loadable under their original installed version.

Not in v1:

- arbitrary pack migration scripts;
- automatic newest-version migration;
- chained path discovery;
- lossy defaults for removed units/items/progression;
- cross-package-id migration.

Future seam: destination declarations may later name any source package id/version. Enabling that will
require trust/author attribution rules, collision policy, richer transforms, and possibly chain/path
selection; the v1 declaration keeps the identity fields needed without promising those semantics.

## Future campaign-editor plan amendment

The editor shell exists in the current integration. Its remaining feature/adoption and visual work must preserve
these accepted requirements:

1. Make the eventual editor available on every supported device/platform rather than enforcing a
   desktop-only gate.
2. At editor entry, assess effective viewport, pointer capability/observation, physical-keyboard
   observation, virtual-keyboard support, orientation, and Web persistence signals.
3. Show one prominent warning when recommendations are unmet or unknown. Phrase unknown physical
   keyboard state as unconfirmed, not absent.
4. Offer **Continue Anyway**, optional per-environment dismissal, and a route back to diagnostics.
5. Recommend—but do not require—a suitably large display, mouse or touchscreen, and physical keyboard.

These belong to the CEUI tracker rows and the accepted UI update. The current plan does not claim
Windows/browser visual acceptance; that remains a playtest gate.

## Ordering and branch strategy

1. Slice 1 is the first release blocker and lands independently.
2. Slice 2 follows on a separate product branch; do not mix it with migration.
3. Slice 3 begins with the save-reference inventory and fixtures, then implementation. If it threatens
   the v0.7.6 repair candidate, keep it on its own branch rather than weakening its validation.
4. The accepted editor/navigation amendment remains the target while visual acceptance and authored-pack
   adoption proceed through the UI/playtest queue.
5. Product work flows through `agent/integration` → `agent/playtest-release` →
   `agent/stable-release`. Windows/browser visual acceptance remains required before promotion.

Each slice needs its own canonical tracker row and non-overlapping claims before implementation.

## v0.7.6 release acceptance

- Exact build stamp and hashes verified.
- Clean-user-data import-to-New-Game journey passes without restart.
- Every installed valid version is visible and launches its own content.
- Invalid/no-playable pack cannot enter the player library.
- Native Windows and Web transfer journeys pass, including cancellation and byte-valid round-trip.
- Direct same-id version migration passes success, unmapped-id, ambiguous-map, topology-change, corrupt
  source, and failed-commit rollback fixtures.
- No duplicate signal errors, stuck modal, input leakage, or focus loss in returned logs.
- Save/relaunch/continue and one representative map completion pass on the package-backed campaign.
