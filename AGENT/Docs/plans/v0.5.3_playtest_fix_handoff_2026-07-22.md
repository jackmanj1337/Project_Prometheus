## P0 — Resume seam (V053-01 + V053-02), one change set

Both bugs are the same root cause: a mid-battle suspend resume boots straight
into `GameMap` without ever re-marking the campaign node as launched.

### V053-01 — resume orphans the campaign node

- Root cause: `CampaignManager.restore_campaign_state()` ends with
  `_active_node_id = ""` (`scripts/autoloads/CampaignManager.gd:788`). A
  between-map restore then calls `launch_current_node()` which re-sets it
  (line 303); a **mid-map** resume via
  `GameState.configure_suspend_resume()` (`scripts/autoloads/GameState.gd:367-424`)
  never does. When the map resolves, `_record_result()` bails at
  `CampaignManager.gd:523` ("no launched node") → empty `_pending_result` →
  `MapResultsScreen` takes the campaign-data-error branch (`Return to Menu`,
  "next battle is unavailable") and the win is lost.
- Fix: add `CampaignManager.resume_launched_node()` that, guarded on an active
  campaign and non-empty `current_node_id`, sets
  `_active_node_id = current_node_id` and logs a distinct event
  (`node_resumed`). Call it from `configure_suspend_resume()` right after the
  campaign envelope restores (around `GameState.gd:397`). The mid-map save
  carries `campaign_id` + `node_id` (confirmed in `resume_battle.json`), so
  the data is present.
- Test (headless): capture a mid-map save on a campaign node →
  `configure_suspend_resume` → emit `map_victory` + `map_resolved` → assert
  `get_pending_result()` names the node and its successor. Repeat for defeat.

### V053-02 — retry on a resumed map wipes the board

- Root cause chain: `GameMap._apply_suspend_resume()` calls
  `clear_suspend_resume()` (`scripts/core/GameMap.gd:374`) but leaves
  `next_map_roster_policy = "suspend_resume"` (set at `GameState.gd:413`). On a
  defeat→Retry reload the payload is empty, so `_spawn_units()` asks
  `is_roster_ready_for_launch()`, which for `suspend_resume` is
  `not next_map_suspend_payload.is_empty()` (`GameState.gd:544-545`) → false →
  spawn aborts, `TurnManager.start_map` never runs → empty board, no objective
  HUD (matches the screenshot + `launch roster not explicitly prepared for
  policy 'suspend_resume'` log line).
- Fix: when the resume payload is consumed on the live map, normalize
  `next_map_roster_policy = "keep_current_roster"` (the roster was rebuilt
  from the payload at `GameState.gd:407`). **Both halves are required** — with
  only V053-01, Retry routes to prep and `begin_prepared_battle` hits the same
  stale-policy wall.
- Test (headless): apply a resume → assert `is_roster_ready_for_launch()`
  still true after the payload is consumed; retry restores ledger round 0 and
  relaunches with units present.

### V053-09 (fold in here)

`MapResultsScreen._quit_to_menu()` (`scripts/ui/MapResultsScreen.gd:250-255`)
never calls `end_campaign()`, unlike `GameOverScreen._on_quit()`
(`scripts/ui/GameOverScreen.gd:304-311`), so the dead campaign lingers in
memory. Add the `end_campaign()` call to match. Mostly moot once V053-01 is
fixed, but the two quit paths should behave identically.

### V053-08 (optional, same area)

Every Continue logs `campaign_restored` twice — once from the menu caller,
once from `GameMap._ready()` re-staging the payload (`GameMap.gd:71-73`). Tag
the re-stage as `campaign_restaged` or skip its log. Harmless; cost real
triage time this round.

## V053-04 — Manual save budget (per-campaign cap of 3)

Three stacked problems:

1. The cap is global: `SaveManager._manual_write_allowed()`
   (`scripts/autoloads/SaveManager.gd:382-407`) counts **every** manual
   `between_map` row regardless of campaign. Scope the count to the active
   campaign — the header carries `campaign_id` (see `resume_battle.json`
   header, and `_slot_index_row` mirrors `header` into the index row at
   `SaveManager.gd:511-520`), so filter the `used` tally by the active
   campaign id. Confirm the id is reachable from `_manual_write_allowed`
   (via `GameState`/`CampaignManager`) at write time.
2. Replace is broken at the cap: `PrepScreen._write_manual_save()`
   (`scripts/ui/PrepScreen.gd:234-245`) writes a new timestamped slot id and
   deletes the old only on success; at the cap the new write is refused first.
   Fix: Replace should reuse the existing slot id (SaveManager already permits
   a manual overwrite of an existing manual slot, `SaveManager.gd:383-388`) —
   atomic, no headroom needed, no orphan on failure.
3. No UI diagnosis: the only feedback is "Save failed." Surface the real
   reason, e.g. "All 3 campaign save slots are in use — delete one from Load
   Game." **Verify Load Game actually offers delete; add it if not.**

Tests (headless): fill a campaign's 3 slots → 4th manual save refused with the
diagnostic; a save in a *different* campaign still succeeds; Replace at the cap
succeeds and leaves exactly one slot for that label.

## V053-03 — Full heal between maps

- Root cause: casual death leaves `hp = 0` in the shared roster `UnitData`
  (`DeathLifecycle` only sets `is_incapacitated` under permadeath,
  `scripts/autoloads/DeathLifecycle.gd:22-25`), and nothing heals between
  maps — `Unit.reset_map_state()` (`scripts/units/Unit.gd:393-396`) never
  touches `hp`. `GameMap._spawn_units()` filters only `is_incapacitated`
  (`GameMap.gd:259`), so a retreated unit spawns at 0 HP and dies to any hit.
- Fix: at campaign next-map launch, restore every roster unit to `max_hp`.
  Put it on the launch path (e.g. in `CampaignManager.launch_current_node()` /
  `launch_prepared_node()` or the roster-policy application), **not** on the
  suspend-resume path — a resumed board must keep its mid-map HP. Also confirm
  living units no longer silently carry damage between maps (today they do,
  via `damage_taken_this_map`/`hp` persistence) — full heal resolves that too.
- Test (headless): a unit reduced below max (and one at 0 via casual death)
  reads `hp == max_hp` after the next campaign launch; a suspend resume of a
  damaged board keeps the damaged HP.

## V053-05 / V053-06 — HUD layout editor

### V053-05 — polled input leaks under the editor

- Root cause: `HudLayoutEditor._input()` consumes non-mouse *events*
  (`scripts/ui/HudLayoutEditor.gd:47-52`), but both consumers underneath
  **poll** every frame, which `set_input_as_handled()` cannot stop:
  `ModalScreen._process()` focus repeat (`scripts/ui/ModalScreen.gd:132-153`)
  and `MapCursor._process()` (`scripts/core/MapCursor.gd:346-370`).
- Fix (two gates): (1) `HudLayoutEditor` acquires/releases the EventBus
  gameplay-modal lock exactly like `GameOverScreen`
  (`GameOverScreen.gd:322-337`) — silences `MapCursor`, which already honors
  `_gameplay_modal_locked()`. (2) `SettingsScreen` pauses its focus repeat
  while the editor it spawned is open — it owns the editor lifecycle
  (`_on_edit_hud_layout`, `SettingsScreen.gd:680-686`) and the base exposes
  the `_modal_focus_repeat_enabled()` opt-out; gate it on the editor's `closed`
  signal.

### V053-06 — toolbar buttons read as dead

- `Scale Panel −/+` no-op with no panel selected
  (`HudLayoutEditor.gd:200-207`): disable them (or show "select a panel
  first") until `_selected_id` is set.
- Drag frames (`MOUSE_FILTER_STOP`, added after the toolbar,
  `_build_handles` lines 107-127) win clicks where they overlap the toolbar —
  the screenshot shows `phase_label`'s frame over the title/Scale−. Give the
  toolbar a reserved strip the frames cannot enter, or clip frames out of the
  toolbar band.
- After both land, **one live Windows check** of Done/Cancel (per decision 3).
