# v0.7.0 playtest and visual-check bundle — work order

## Purpose

Consolidate **one** bundle that collects everything currently waiting on a human with
a display. Several rows have been sitting in `in_review` for weeks for the same
reason — nobody in a container can look at a screen — and they have been accumulating
into separate future "visual passes". This bundle exists so that one session at a
Windows machine, with a phone and a pad to hand, closes all of them at once.

Owner instruction, 2026-08-05. Supersedes nothing in
[`v0.7.0_prebundle_handoff_2026-08-04.md`](v0.7.0_prebundle_handoff_2026-08-04.md) —
that work order still defines what must be true before the bundle is cut. This one
defines **what goes in it**.

Tracker row: `V070-BUNDLE-EXECUTION-2026-08-04`.

## The bundle contains

### 1. The Windows build

Both executables from the exact frozen candidate, exported from that commit and not
reused from an earlier round:

- `Project_Prometheus_v0.7.0_debug.exe` and `Project_Prometheus_v0.7.0.exe`
- `SHA256SUMS.txt`, `BUILD_INFO.json`, and both artifact manifests
- Each artifact's filename, size, SHA-256, version, baked commit, build mode and build
  timestamp recorded in the manifest

The debug executable is the one that traces a whole session, so the checklist must say
which executable each item wants.

### 2. The image albums

Every album that has been generated, so the owner reviews rendering in one place
instead of re-deriving it:

- The regenerated labeled Playwright responsive album for v0.7.0 — all cases, with
  `report.json`.
- The v0.6.1 reference album, alongside it, for comparison. A passing navigation count
  is not the check; frame dimensions and visual changes are.
- The mobile-web probe captures (desktop, iPhone-emulated landscape, and the
  safe-area-fed case) produced on 2026-08-04.
- Any terrain-variant captures that exist.

Albums are **evidence for the decision sheet in §5**, not decoration. Every image that
drives a decision gets a stable filename the decision sheet can cite.

### 3. The display-gated task list

A manifest of every open row that cannot close without a display, so the owner knows
what the session is actually buying. Current occupants:

| Row | What a display settles |
|---|---|
| `IMPL-TERRAIN-VARIANTS-AND-PACK-TERRAIN-2026-08-01` | tile sizing and atlas regions |
| `IMPL-FILEDIALOG-ESCAPE-TEXTINPUT-2026-07-29` | Windows event order, OS keyboard, `escape_consumed_by` |
| `BACKLOG-INPUTMAP-CONFIRM-CANCEL-DOUBLEBIND-2026-07-24` | joypad button 1 on accept/back, with a real pad |
| `PP-V060-CHECKLIST-CARRYFORWARD-2026-07-29` | the two carry-forward items still open |
| `MOBILE-WEB-UX-GAPS-2026-08-03` | physical safe areas and legibility of the fitted scale |
| `IOS-DEVICE-PWA-VERIFICATION-2026-08-03` | install, offline relaunch, soak, save durability |
| `DEDICATED-TOUCH-CONTROLS-2026-08-03` | real-device touch validation |

One row is deliberately **absent**: `IMPL-FOG-RENDER-2026-08-02` needs a visual pass but
is still `planned` — nothing is built to look at. Fog stays out of this bundle, as the
pre-bundle handoff already required.

**`IMPL-VIEWPORT-ANCHORING-2026-07-31` was removed from this list on 2026-08-06** (owner
decision) and closed as **superseded**. It had been paired with terrain variants on one
shared pass; terrain variants still needs that pass, so the table entry above stands on
its own now. The reason it left: what its pass would have validated is the **1280×720
design floor**, and the project has retired that floor. `SMALL-SCREEN-UI-REDESIGN-2026-08-05`
replaces it with a size-class model (Compact <600 / Medium 600–1023 / Expanded ≥1024
logical px, floor 360×640) — described in `AGENT/Docs/design/responsive_ui_redesign_2026-08-06.md`,
which is still on the unmerged branch `agent/from-integration/small-screen-ui-redesign`.
Asking the owner to ratify anchoring against the old floor would buy a verdict on a
target that no longer exists, and the ~11-scene anchor conversion is now folded into each
screen's redesign conversion so it happens once.

What that row **shipped** is unaffected and is still in the build: `content_scale_factor`
as a persisted player setting with its derived first-launch default, `aspect=expand`,
`snap_2d_transforms_to_pixel`, the `MenuScale` reconciliation, and the Viewport Scale
control in Settings. Those are the foundation the redesign is built on, so the checklist
items that exercise them stay.

Note separately, because it is not image-derived and must not get lost: the `[PCM-7]`
owner call on `IMPL-CROSSING-RESOLVER-2026-08-01` (does an effect-less fired trigger
make a move permanent?) is a rules decision that can be answered in the same sitting.

### 4. The master checklist

**A superset, not a successor.** `playtest_checklist_v0.7.0.md` as written drops the
v0.6.1 items that were closed on returned v0.6.0 log evidence. For this bundle it must
instead carry **every v0.6.1 item**, plus the v0.7.0 additions, with each item marked:

- `NEW` — first appears in v0.7.0;
- `UNPROVEN` — shipped in v0.6.1 and never reported back (most of them: there is no
  `AGENT/Docs/playtests/evidence/v0.6.1/`);
- `REGRESSION` — closed on real evidence, re-run only to confirm nothing broke.

Keep the fixed sections: build identity, Windows, controller, web/PWA, mobile device,
campaign-pack lifecycle, save recovery, carry-forward, return requirements. Add the
v0.7.0 additions: the user-data directory rename and its migration, the Viewport Scale
setting, terrain variants, the mobile-web touch mode, the fed safe-area insets, and the
fitted mobile default scale.

The existing checklist wording that calls 1280×720 "the design floor" describes what
v0.7.0 *is* and is fine to test against — but it is no longer a project commitment (see
§3), so nothing in the return should be read as ratifying it.

### 5. The decision sheet

A list of the decisions the owner must make **from the images in §2**, each naming the
image that shows it and offering concrete options rather than "does this look right".
Known entries:

- **Window sizing.** Load Game and Campaign Library should be modest centered dialogs,
  not near-fullscreen panels. Accept, or name the target proportion.
- **Main-menu proportion at wide aspect ratios.** In the 2026-08-04 iPhone-landscape
  capture (1704×786 logical) the panel occupies a narrow central column with large
  empty margins. Accept as intended, or specify how the panel should grow.
- **Viewport Scale default and range** — is the identity diagonal the right desktop
  default, and is the slider's range useful at both ends? This one now feeds
  `SMALL-SCREEN-UI-REDESIGN-2026-08-05` rather than the closed anchoring row: the size
  class is derived from `window_size / content_scale_factor`, so the default this
  question sets is what decides which class a given device lands in.
- **Terrain variants** — do visually distinct variants of one terrain read as the same
  terrain, given they must behave identically?
- **Mobile default scale** — the fitted default resolves to 1.5 on an iPhone landscape
  canvas. Is that physically legible, or does it need a floor?
- **PWA icons** — currently placeholder Project Prometheus icons. Final art is an owner
  call, and on iOS the apple-touch-icon overrides manifest icons entirely.
- **Safe-area padding appearance** once real insets are fed on a device.

Anything the owner decides here becomes a tracker row in the same session; a decision
recorded only in a returned document is how the last two rounds lost their outcomes.

### 6. The campaign packs

Updated copies of every pack needed to exercise the checklist end to end — install,
select, launch, save, exit, reload, continue, switch, and the missing-pack and
invalid-pack recovery paths.

**Two constraints bind here and must be resolved before assembling, not during:**

- `IMPL-ZERO-CONTENT-BASE-PACK` is incomplete. The extracted `proving_grounds` pack
  **does not play yet** — battle encounters (placements, factions, turn order,
  objectives, rewards) are not emitted, so its maps are terrain and start tiles only.
  Either finish the encounter slice first, or state plainly in the checklist which
  lifecycle steps the shipped pack can and cannot exercise.
- `Campaign_Pack_FE` is **internal-only**: never public, and never in a shipped build.
  A bundle that reaches only the owner is within that rule, but it must be labelled so
  it cannot be forwarded, and the checklist must not ask for anything that would
  require redistributing it.

Include a deliberately invalid pack fixture too — the invalid-install path is a
checklist item and cannot be exercised without one.

### 7. Onboarding instructions

Written for someone who has not been in the repo. Two of them.

**Windows.** Where to unzip; which executable to run for which items; how to verify
`SHA256SUMS.txt`; where saves, settings, installed packs and logs now live —
`%APPDATA%\Godot\app_userdata\Project Prometheus\` — and that this is a **rename** from
`Fire Emblem RPG`, so the first launch migrates the old directory and that migration is
itself a checklist item; how to install a campaign pack; and exactly what to return
(the whole log directory, not a summary).

**Web app.** How to run it — the local loopback server, or the tailnet host — and that
`FREEZE-WEB-DISTRIBUTION-2026-07-26` forbids publishing it anywhere else; that the PWA
items require **HTTPS**, because a plain-HTTP page rendering proves nothing about
installation, service workers, offline launch, or durable storage; how to install to the
home screen; how to confirm the service worker and an offline relaunch; and that saves
live in browser storage, so the export path is the only way to keep them.

## Cutting sequence

1. Finish the must-dos in the pre-bundle handoff that still gate the candidate.
2. Freeze the candidate and record the commit.
3. Export Windows and web from that exact commit; reject stale artifacts.
4. Regenerate the album from that commit; diff against the v0.6.1 reference.
5. Write the master checklist, the display-gated task list, and the decision sheet.
6. Assemble through the bundle tooling and verify the manifest names the exact exported
   artifacts, the checklist, the albums, and the packs.

## Definition of done

The bundle is complete when a person with a Windows machine, a phone and a pad can, from
the bundle alone and without asking a question:

- verify they are running the right build;
- work through every checklist item knowing which executable each needs;
- look at each image the decision sheet cites and answer it;
- install, run and recover a campaign pack;
- and return evidence in a form that closes the rows in §3.
