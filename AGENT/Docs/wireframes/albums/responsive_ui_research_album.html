SMALL-SCREEN-UI-REDESIGN-2026-08-05 · design pass 2

Stop authoring for a screen.
Author for a size class.

Pass 1 asked how to fit the UI on a phone. That was the wrong question: the same build is mis-scaled in landscape too, and a Linux handheld and a phone cast to a TV are two more shapes with no answer. This pass replaces the fixed design floor with two dials the player already half-owns — viewport shape and content scale — and one derived size class every screen responds to.

Two corrections the capture forced

The map band is 26%, not 55%

Pass 1 assumed the portrait canvas took the 55% that portrait_top defines. The bridge reports a logical viewport of 2358×1326 at scale 0.5 — 663 backing pixels tall, 26% of the screen. The default game_view_preset is auto, which leaves the active controller combination's own viewport alone, and that combination reserves nearly three quarters of the screen for controls. Every reference disagrees: DS 55%, Awakening 54%, portrait_top 0.55.

That is a controller-layout defect rather than a UI-redesign item, but it lands in the same build and it makes portrait look worse than the layouts alone would.

Landscape is not a working control

Pass 1 treated landscape as the case that already works. It clears the old floor — content 1.5, viewport 1704×786 — so nothing clips, and that is the only sense in which it works. The menu panel occupies about a fifth of the screen, type still renders near 8 CSS px, and the d-pad is drawn on top of the menu, which the owner's own reference notes rule out in the first line.

This is why the scope moved from a portrait patch to a redesign: there is no orientation where the current UI is right, because there is no responsive model at all. Screens are authored at one size and centred in whatever they are given.

What the registries force

Constraints from this codebase, not from taste. Each rules out a layout that would otherwise be the obvious choice.

  • Stats are a vocabulary, not a layout

    StatRegistry.display_stat_ids() returns 11 ids today. Every sheet flows that list into whatever column count the size class allows — 2 in Compact, 3 in the second surface, 2×5 in Expanded. A hand-placed grid silently drops stat 12.

    D4 · E2 · E3

  • Images are always present and never informative

    Corrected 2026-08-06. The campaign editor will auto-insert a plain colour rectangle with an author-chosen RGB and alpha, and a pack can be rejected for lacking one — so layouts may rely on a filled box of known aspect and need no empty-state branch. They must never rely on the image to identify anything: no icon-only controls, no portrait-only rows, every image-bearing row carries a text label that alone is sufficient.

    D1 · D2 · D3

  • Nothing covers the controls

    Controls never cover the canvas (the existing rule) and menus never cover the controls (new, 2026-08-06). Strict separation in both directions is the default; expanding over the control band is opt-in. Every Compact layout must therefore work without the band's space.

    C · E

  • Fonts are pack-swappable

    The raw_font handler lets an author replace the face. Every layout must survive ~1.3× text extent, and truncation must eat the value before the label.

    all

  • Menu length is data

    Prep activities, difficulty tiers and map actions come from open registries. Every one is a scrolling column — no fixed grids, no radial menus, no “exactly five”.

    B · D

  • One pack is active at a time

    No cross-pack merge, so no screen ever shows two packs side by side, and the library shows no dependency controls by design.

    D1

  • Density follows the input device, not taste

    Awakening runs 17.6px rows because nothing there is tapped. Menu Mode picks a token set; it is not a look-and-feel preference and must not be presented as one.

    C

The info panel, resolved

Ship the overlay, build toward the second surface

The 3DS references settle what pass 1 could only reason about. combat-forecast-dual-surface.png shows the forecast on the map surface and the target's entire stat sheet below it, simultaneously — a popup cannot do that, and neither can a drawer. The bottom sheet carries 7 stats, 4 combat stats, a portrait, a name block and 5 inventory rows in 320×240, at a 17.6px row pitch, because nothing on it is ever tapped.

Still ship E2, the full overlay, first. UnitDetailsScreen is already a ModalScreen with a working responsive frame; it needs re-authoring, not re-plumbing, and it is the only option that is free.

E3 is now an opt-in, not the default. Nothing covers the controls unless the player says so, and the second surface borrows the control band by definition. It stays the best experience and the thing to build toward — but the default path is the GBA/DS model: everything inside the game viewport, paged. Both references are honoured and the player picks which one they are playing.

Drop the drawer. It occludes the tiles you are deciding about, which is the exact problem the two-screen layout exists to solve.

What pass 2 got wrong about More Info

Worth stating plainly, because the wireframes were confidently incomplete.

It is a mode, not a screen

Pass 2 drew UnitDetailsScreen as a stat sheet with an inventory list. The real scene is Panel/HBox = a scrolling content pane (title, class, stats, inventory, skills, weapon ranks, Pair Up, Back) beside an InfoVBox carrying a title, a modifier breakdown and a description. Skills and weapon ranks were missing from every pass-2 wireframe.

Every visible entry is a BBCode [url] link. Selecting one fills the info pane from MoreInfoContent and, for stats, a StatBreakdown that shows where the number came from — with green and red flags for stats an active buff or debuff is currently moving. That breakdown is the single densest thing in the UI and pass 2 had no place for it.

More Info is also a priority cycle across three hosts — combat forecast → character sheet → terrain HUD — and terrain already implements paging (Hidden → Description → Movement → Hidden), shipped in v0.2.2. Any Compact answer has to fit that existing model rather than invent a parallel one.

And the codebase already has an ad-hoc size class. UnitDetailsScreen._update_responsive_layout() stacks the two panes when the viewport is narrower than a hard-coded 900.0. Both panes carry a 240px minimum, so side-by-side needs ≥500 logical px and cannot fit Compact at all. That one line is the whole thesis of this pass in miniature — and the first thing the size-class seam should replace.

Still open

Four things I cannot decide alone. The first blocks implementation.

  1. Close the anchoring row on the current bundle, or fold it into the redesign?

    What it is. IMPL-VIEWPORT-ANCHORING is in_progress, waiting on the v0.7.0 Windows visual pass, and it claims project.godot, MenuScale.gd, SettingsManager.gd and scenes/ui/ — every screen in the game.

    Close it first: its ~11-scene anchor conversion lands on the old floor, then the redesign re-anchors the same scenes a second time. You pay for the conversion twice and the visual pass validates a floor already abandoned — but the row's other work (MenuScale reconciliation, the div-by-zero and corrupt-cfg guards) is banked and out of the way.

    Fold it in: each screen is anchored once, correctly, during its redesign conversion. Nothing is done twice. The cost is that a row with real merged work gets closed as superseded, and its unmerged branch has to be picked over for the parts worth keeping rather than merged wholesale.

    Consequence either way: nothing else starts until this is decided, because both rows write the same files. This is the only true blocker on the list.

  2. Does Information Density ship in v1, or only its plumbing?

    What it is. Awakening's Interface: Full / … — a player setting for how much detail each panel shows, orthogonal to how big anything is.

    Ship it: the player who wants a clean map gets one, and it is genuinely the right feature. It also multiplies verification: every screen must be checked in 3 densities × 3 size classes × 2 menu modes. That is 18 states per screen, and the visual pass is the project's scarcest resource — it needs a Windows machine, a phone and a pad in one session.

    Plumbing only: build the density token as a constant that reads Full, wire every panel through it, expose no control. Verification stays at 6 states per screen. Adding the setting later is then a one-line change plus a Settings row — because the panels already ask.

    Consequence: the reverse order is what is expensive. Retrofitting density into panels that hard-coded their content means touching every screen again. Recommendation: plumbing now, control later.

  3. How does a player discover the opt-in that lets menus cover the controls?

    What it is. The default is now strict separation, so Compact menus live in the game viewport and get roughly 7 rows instead of 9. The setting that buys back the controller band is the difference between a cramped phone UI and a comfortable one.

    The trap: a setting nobody finds is a default nobody chose. The players most helped by it — phone players on the smallest screens — are the least likely to walk a Settings list looking for it.

    Options: leave it in Settings and accept low discovery; or offer it once, in context, the first time a menu has to scroll in Compact. The second is better UX and is also a prompt that can annoy, and this project has already been bitten by controls that change on their own reading as a bug.

    Consequence: if discovery stays low, Compact must be genuinely good at 7 rows — which is a real constraint on every layout in album D, not a footnote.

  4. Who fixes the 26% map band, and when?

    What it is. Measured this session: the portrait canvas gets 26% of screen height. All three references and the portrait_top preset say 54–55%. The cause is that game_view_preset defaults to auto, so the active controller combination's own viewport wins, and that combination reserves roughly three quarters of the screen for controls.

    Why it is awkward: it is a controller-layout defect, so it belongs to MOBILE-WEB-CONTROLLER, not here. But it lands in the same build, and every map wireframe in album E assumes the 55% it does not currently get.

    Fix it in the controller row: correct ownership, and the redesign's map layouts become testable. Fix it here: faster, but a redesign row editing controller layout data is exactly the kind of claim overlap that produced the seven-row collision in the first place.

    Consequence of deferring: album E cannot be validated at all — a 26% band cannot show the 12×14 tiles the layouts are drawn against, so the map work would be building blind.

Sequencing

What this costs, in order

1. Reopen or supersede IMPL-VIEWPORT-ANCHORING-2026-07-31. It is in_progress, gated on an owner visual pass, and it owns both SettingsManager.gd and the 1280×720 floor this pass replaces. Nothing below can start cleanly until that is resolved — it is the one hard blocker.

2. Land the size-class seam. One autoload, three classes, a signal, and the density token sets. No screen changes. This is small and everything else depends on it.

3. Convert screens, cheapest first. Main Menu, Settings, Campaign Library, New Game — the four with no combat coupling — then roster, unit sheet, prep hub, then the map HUD and its menus last, because they interact with the controller band.

4. Fix the 26% band alongside the map HUD work, in the controller row.

The seven-row path collision from the original tracker note has not gone away, and it gets worse with a redesign that touches every screen. Converting one screen per branch, in the order above, is what keeps it merge-able.
