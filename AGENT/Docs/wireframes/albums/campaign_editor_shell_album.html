Campaign Editor · Shell & Lifecycle · Wireframe Set

The editor, end to end, at every display it will meet

The campaign editor has exactly one responsive state and one hard floor — 1920 × 880 effective pixels. This set draws its whole lifecycle at that floor, draws each of its seven workspaces, and then shows what the shell does with the room an FHD, QHD or 4K display actually gives it. The frames are real CSS layout at true effective pixels, so every number quoted in a caption was measured after mount, not estimated.

Sections B–F are still open — CEUI-9–12, 17–21, 23–31, 33–36, 39, 40 — and so are the twelve NMTE residues scheduled as S11. Anywhere this set shows a dashed red outline, the region's position and role are ruled and its interior is not. Do not read a dashed region as a design proposal.

The gate has not lifted. UBS-8 and the UUI-15 album hold release only when the whole CEUI walk closes, which it has not. Drawing the shell ahead of that was an owner decision, recorded as such — not the gate being met.

New questions are raised, not answered. Nothing about the editor's behaviour above its floor has ever been ruled. Section 7 collects ten findings this pass produced, each with options and a recommendation, for an owner walk. They are marked proposed throughout.

SHEET 1

The display model

CEUI-5 · CEUI-S1 · CEUI-S2 ratified

Three ratified pieces combine into one arithmetic, and the arithmetic is what makes "FHD, UHD and 4K" a tractable question rather than an open-ended one.

  • [CEUI-5] — the floor is 1920 × 880, a maximized browser window on the most common desktop display, with a ~200 px allowance for tab strip, omnibox, bookmarks bar and taskbar. Below the floor the editor shows an explanatory minimum-size state; it never degrades into a compromised layout.
  • [CEUI-S1] — the player's Menu Scale does not reach the editor. The editor owns its own scale knob, built as a fourth token column through the same assembler.
  • [CEUI-S2] — the floor is tested against window ÷ editor scale, not raw window pixels. Effective pixels are the unit of this whole document.

The two factors multiply, and only one of them is ours

The OS/browser scale factor sets how many physical pixels a CSS pixel spends. The editor scale sets how many CSS pixels an effective pixel spends. The product is what the author's eye actually receives.

effective = windowcss ÷ s  ·  physical-per-effective = DPR × s

Combining the two gives the result that governs this sheet. Hold physical-per-effective ≥ 1.0 — never render editor type physically smaller than an FHD display at 100% shows it — and the reachable effective viewport collapses to a single expression:

max effective viewport = physical resolution − (chrome allowance × DPR)

So the display's physical resolution — not its CSS window, not its OS scale setting — is the real ceiling on how much editor an author can have. Two displays that report identical CSS windows are not equivalent: the 4K one can trade its scale knob for room and the FHD one cannot. That is the entire FHD-versus-4K story, and it is why this set has exactly three width columns rather than a continuum.

Three results worth stating plainly. (1) A 4K display at Windows' default 200% scaling produces exactly the floor window — the same 1920×880 an FHD display gives at 100%. The floor was derived from FHD and 4K lands on it by coincidence of arithmetic. (2) 4K at 150% and QHD at 100% are the same window, so the whole FHD/QHD/4K range reduces to three distinct effective viewports. (3) The only row that fails outright is FHD at 125% — a common Windows default on 1080p laptops — and it fails on height, by 216 px, not on width.

Reading a frame

Label text inside frames is set at 16–18 effective px so it survives the 0.55× reduction. That is an annotation size, not the editor's type size — real editor body type is 14 effective px and is drawn as grey bars. Where a measurement matters it is reported numerically in the caption rather than trusted to the eye.

SHEET 4

The lifecycle, eleven states

CEUI-S3 · S4 · S5 · S6 · S8 · S9 · S10 · S13

Every frame is 1920 × 880 effective — the floor, and the state in which the editor must be proven. The editor takes a copy, the author works in staged transactions, tests inside an embedded session, and leaves only by an explicit export. There is no implicit write-back anywhere on this path.

There is no entry transition, by [CEUI-S13]. The editor is reachable only from the main menu, where no pack is active, so it never has to end a run and never shows a confirmation to do so. An earlier draft of this sheet opened with that dialog; it was drawn from [CEUI-S9] call 2's quit-to-shell framing, which described a transition the entry point makes impossible. The substance of call 2 survives and is stronger for it — the editor still requires no active campaign, as a precondition rather than as something the editor performs. A player mid-campaign quits to the menu through the shell's own existing confirmation, and the editor adds no second one.

That precondition is ratified and unbuilt — see EW-10. [CSA-28] clause (f) ruled that quit-to-shell deactivates, but DataManager.deactivate_campaign_package() has no production caller and MainMenu.gd reads only the installed-pack registry. Today the main menu is reached with content still loaded. Nothing depends on that yet; the editor would be the first thing that does.

SHEET 6

FHD → QHD → 4K

width response proposed

Four width responses, one per kind of content

The editor is a single size class, so extra width cannot be answered by a breakpoint. It has to be answered by what the content is. This pass proposes four rules, and every workspace is one of the four.

ResponseRuleWorkspacesAt 3840 effective
Canvas fillsTakes all remaining width and height. More width is more map, more graph, more zoom headroom. Maps, GraphCentre canvas reaches
Grid reflowsFixed tile size, column count grows with width. Never stretches a tile. Assets → columns
Form capsSingle-column forms cap at an 880 px measure and centre. Extra width becomes gutter, then a second document column. Content, ReleaseSplit offered above 2400 px of centre
Table extendsFixed key column, locale columns added until width runs out. Localization → locales
Simulator is fixedSized by the simulated size class, not by the editor. Extra editor width becomes device surround. TestGame view unchanged; 1:1 becomes possible

The fifth row is the one most likely to be got wrong in implementation. [CEUI-S3] put a real playable session inside the editor and [CEUI-S2] made the editor's own scale independent of it, which means the embedded game view derives its size class from its sub-viewport. Stretching that view to fill a 4K editor would silently change the size class the author thinks they are previewing — the exact failure [DLUX-15]'s per-size-class preview obligation exists to prevent.

SHEET 8

The proposed editor token column

proposed

A fourth column, not a second scaling system

[CEUI-S1] ruled the editor is a fourth DENSITY_TOKENS column plus its own multiplier through the same assembler, following [UUI-11]'s precedent. It did not fill the column in. These are the values every frame in this album was laid out from — proposed, and the first thing an implementation would need.

ResponsiveLayout.DENSITY_TOKENS["editor"]
Tokentouchcontrollereditor proposedWhy

min_target is the one that needs an owner's eye. Touch is 44 (Material 48dp / Apple HIG 44pt), controller is 0 because there is no pointer. The editor is proposed at 24 — a real pointer target, but well under the touch minimum, justified by [NMTE-S2]'s ruling that a mouse and physical keyboard are a stated assumption. That assumption is stated, not enforced: [CEUI-S2] kept Branch K's input-mode warning alive precisely because an author can arrive on a touch device anyway. A 24 px target is then a hit-rate problem, not a layout problem. See EW-9.

Where this album and the engine disagree, the engine wins and the album is stale — that has happened once before and the proof set records it as a finding.

What these frames are. Specifications for a walk, not screenshots and not a component library. They are HTML because HTML lays out and measures a dense dock layout quickly — the UI is Godot scenes. Where a frame and a future build disagree, the frame is the target and the difference is work; where a frame and a ruling disagree, the ruling wins.
