Four screens drawn across the full range of size classes, aspects and orientations the responsive model has to survive. Between them they exercise every archetype in the game: a plain menu, a list/detail record screen, the worst-case settings list, and the map HUD with its control region. Validate the drawing conventions here before the remaining twenty screens are drawn to them.

01

How to read a frame

Every frame is drawn at a uniform 0.5× of its logical pixel size, so any two frames on this page are directly comparable by eye. Logical pixels are what the game lays out in — backing size ÷ content_scale_factor — not device pixels.

Device edge — the physical screen.
Game view — the Godot canvas. All engine UI lives here.
Control region — dead space the game view declined. DOM, outside the canvas.
Safe area — interactive content insets to here; art bleeds past it.
Focused row — the ▸ marker is the focus ring in controller mode.
Role tag — the theme_type_variation that paints that region.
Reachability risk — this change applies live, then confirms in 15s or reverts.

The one rule every frame obeys

The player picks the game view's size and aspect; whatever is left over is the control region. Controls cannot cover the canvas because they only ever occupy what the canvas declined, and nothing covers the controls because the canvas never grows into them. Strict separation holds in both directions by construction rather than by rule — which is why portrait and landscape are two outcomes of one model, not two designs.

02

The six viewports, true relative scale

Size class is derived from logical width alone: Compact < 600 ≤ Medium < 1024 ≤ Expanded. A 24px hysteresis band on both sides stops a window parked on a boundary from oscillating. Note that phone landscape is Medium, not Compact — 852 clears the boundary comfortably.

03

Density tokens — the only source of metrics

No scene carries a hard-coded pixel value. Menu Mode picks the column; Menu Scale multiplies it; size class picks the layout. Proposed the dense column is new — it serves surfaces that are wall-to-wall equal-weight targets, which is how the keyboard fits 360px without dropping below the 44pt minimum.

Finding — the published Compact row budget is optimistic by half a row

The design doc's budget block spends header 56 + footer 56, leaving 240px of content and 4.3 rows. But DENSITY_TOKENS publishes header 72 / footer 64. Against the real tokens a 352px menu region leaves 216px → 3.9 rows, not 4.3. Every Compact frame below is drawn against the token values, so it shows 3 full rows and a partial. The doc and the code disagree and one of them needs correcting — the frames assume the code is right.

06

Settings

Dual-themed Paged

The worst case, and the best test. 25+ rows against a ~4-row Compact budget; controls whose own movement re-classes the screen displaying them; and the only screen that crosses the theme boundary — chrome-themed from the Main Menu, pack-themed from inside a campaign.

Sections are pages — UUI-19

Six sections become six pages everywhere. Compact shows a section index, then that section's page, with Back. Medium and Expanded show a tab strip. This retires the 25-row scroll: six sections at ~5 rows each, never twenty-five in one window. Settings is therefore not a UIREC list/detail record screen — it is a tabbed pager, a deliberate third composition.

Why Settings argues hardest for derived metrics

The same screen renders in two themes depending on how it was reached. Identical structure, identical metrics, different paint — exactly what today's baked content_margin values cannot deliver without two copies of the scene.

Confirm-or-revert is keyed on reachability risk, not on section — UUI-18

Today confirm: true is set on exactly two schema rows, window_mode and resolution (SettingsScreen.gd:153,162). That misses the setting that can strand a player most completely: Control Style = Off on a touch-only device removes every control there is, and it lives in Controls, not Display. The trigger becomes a reachability_risk property meaning this change can make the UI hard or impossible to get back from, wherever the setting lives.

The constraint that makes the dialog actually work: it must be exempt from the setting it is confirming. Viewport Scale 4.0 applied to the dialog renders the dialog itself unreadable, and Menu Mode = controller drops min_target to 0 — so the safety net would fail in precisely the cases it exists for. The dialog renders at a fixed safe scale with 44pt targets regardless of what the pending change did.

07

Map HUD

Pack-themed Converted last

Sequenced last in the conversion order because it is the only screen that interacts with the control region directly. Panels are free-positioned but stored as viewport fractions and clamped on every resize, which is what stops the stranding recorded in finding V070-08.

Four live defects this sheet has to resolve

(1) The layout editor's toolbar is PRESET_TOP_WIDE with unwrapped children, so “Done” clips off the right edge at high viewport — an editor that cannot be exited. (2) The toolbar overlaps the phase panels. (3) A panel reads “Viewport: Bottom Left” while sitting mid-left. (4) Panels strand on a mid-edit resize, because HUD._reflow_layout re-applies _active_layout while the editor drives panels through set_panel_layout — so a resize re-applies a layout that is not the one on screen.

Archetype — free-position panels over a tile map

Turn/phase · objective · unit info · terrain · forecast. The 12×14 tile board is what the 26% band could not show.

08

The role list — a versioned API

Authors cannot edit scenes/ui/, so they cannot invent roles. Themes are distributed separately and on their own cadence, which means a rename breaks packs the build has never seen. The list therefore rides format_version / builder_content_version and is named semantically — never visually.

What is deliberately not drawn
