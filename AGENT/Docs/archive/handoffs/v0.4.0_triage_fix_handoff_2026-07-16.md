## Purpose

Implement the owner decisions from
[`playtest_v0.4.0_triage_review_2026-07-16.md`](../../Code Reviews/playtest_v0.4.0_triage_review_2026-07-16.md),
then cut one focused Windows rerun that can close the v0.4.0 smoke gate. Work
against the v0.4.0 build lineage; do not mix later campaign/save development into
the artifact.

The returned `d12eb33` build is not release-accepted. Its boot, tactical input,
combat, suspend/Continue, display, and logs were broadly sound, but victory
cursor ownership and reward observability failed, Character Sheet More Info was
mouse-only when text overflowed, and required victory evidence was absent.

## Settled owner decisions

1. Full-screen gameplay modals use a reusable cursor-suppression contract. The
   results overlay must acquire it before becoming visible.
2. Victory shows `Gold earned` and `Total gold`; the Map Menu also exposes the
   read-only total balance. Do not add a persistent tactical-HUD gold counter.
3. Keep suspend gated for v0.4.0. `B1-SUSPEND-LOCAL` and
   `B1-SUSPEND-ANYTIME` are separately tracked; lifting the gate is not part of
   this fix pass.
4. More Info descriptions scroll independently with Page Up/Page Down, right
   stick vertical, and mouse wheel. A focused reading mode remains a later
   `UI-INSPECTION-FOCUS-SCROLL` evaluation.
5. Returned-checklist completeness stays a manual, case-by-case decision. Do
   not build a linter.
6. Keep the `armsthrift` warning in development builds, but exclude
   unimplemented skills from release-facing selectable content.

## Required implementation order

### 1. Establish shared gameplay-modal cursor suppression

Replace `GameOverScreen`'s ordering-dependent local consumption with an explicit
contract acquired before the overlay is shown. Prefer one reusable modal-lock
signal/API with balanced acquire/release semantics over a results-specific
direct node lookup. It must suppress both event handling and the held-direction
poll in `MapCursor._process()`.

Touchpoints to inspect:

- `scripts/ui/GameOverScreen.gd`
- `scripts/core/MapCursor.gd`
- `scripts/autoloads/EventBus.gd` or the existing shared modal owner
- `scenes/ui/GameOverScreen.tscn`
- other full-screen modal callers, to avoid creating a competing lock model

Set the full-screen results backdrop to stop pointer events. Retry and Quit
replace the scene, but keep the API symmetric so another modal can release it
without scene replacement. If nesting is possible, use ownership/counting rather
than a single boolean that one modal can incorrectly clear for another.

Required tests:

- Opening results acquires cursor suppression before visibility/focus.
- Keyboard and gamepad direction events cannot move `current_tile`.
- A held direction processed across frames cannot move `current_tile`.
- Pointer input is captured by the full-screen overlay.
- Existing level-up/promotion-before-results sequencing remains green.

### 2. Introduce an immutable committed-reward receipt

Do not let the UI reconstruct the award from map data. After the ledger commit
succeeds, publish an immutable receipt containing at least:

```gdscript
{
    "gold_earned": committed_delta,
    "total_gold": resulting_balance,
    "items_awarded": committed_items.duplicate(true),
}
```

A separate reward-committed signal is safer than changing a widely consumed
`map_resolved` signature. The results screen may cache the receipt while waiting
for progression modals, then render it when results are presented. Never display
an award receipt when the ledger transaction fails.

Touchpoints to inspect:

- `scripts/core/TurnManager.gd`
- `scripts/autoloads/ResourceLedger.gd`
- `scripts/autoloads/GameState.gd`
- `scripts/ui/GameOverScreen.gd`
- `scenes/ui/GameOverScreen.tscn`

Required tests:

- Successful award displays `Gold earned` and `Total gold` accurately.
- A zero-gold map displays an honest zero result rather than stale prior data.
- Failed ledger commit does not claim a reward.
- Repeated victory-condition evaluation does not award or announce twice.
- Deferred results presentation retains the correct receipt across queued
  level-up/promotion screens.

### 3. Add a read-only Map Menu balance surface

Expose `Total gold` in the Map Menu using the centralized ledger/GameState value.
Keep it informational: no transaction logic belongs in the menu. Structure the
presentation so prep, base, and shop screens can later reuse the same read-only
resource formatting instead of copying balance reads and labels.

Touchpoints to inspect:

- `scripts/ui/MapMenu.gd`
- `scenes/ui/MapMenu.tscn`
- the party-resource/ledger API

Test initial display, refresh after a committed award where the menu remains
relevant, and large/zero values. Check every supported Menu Scale for clipping.

### 4. Make More Info overflow accessible without a mouse

Preserve arrows/d-pad for selecting entries. Add independent description
scrolling:

- keyboard: Page Up / Page Down;
- gamepad: right-stick vertical, using the shared deadzone/repeat conventions;
- mouse: existing wheel behavior.

Only show the scroll hint/indicator when the description's scroll range is
non-zero. Reset or clamp the scroll position when changing entries so a new
description does not open at an unexplained stale offset. Do not introduce the
deferred focus mode in this pass.

Touchpoints to inspect:

- `scripts/ui/UnitDetailsScreen.gd`
- `scenes/ui/UnitDetailsScreen.tscn`
- `scripts/tests/test_unit_details_screen.gd`
- `project.godot` and input-display helpers if named actions are added

Required tests:

- Long content remains bounded and creates a non-zero scroll range.
- Page Up/Page Down change the description scroll value without moving the
  selected entry.
- Right-stick vertical changes the description scroll value with deadzone and
  held-input cadence applied.
- Short content hides the affordance and does not consume unrelated input.
- Changing entries resets/clamps the prior scroll value.

### 5. Gate unimplemented skills from release-facing content

Retain `_apply_unimplemented` diagnostics in development. Add or reuse a content
availability rule so skills without behavior cannot appear in release-facing
selection/loadout surfaces. Do not hardcode a one-off UI check for `armsthrift`;
the gate must cover future unimplemented skill entries through data/registry
metadata or a shared capability query.

Touchpoints to inspect:

- `scripts/skills/SkillHandler.gd`
- skill data/resources and registries
- every player-facing skill selection/loadout source
- debug/test fixtures that intentionally execute stub skills

Required tests:

- `armsthrift` and another synthetic unimplemented entry are excluded from
  release-facing choices.
- Implemented skills remain selectable.
- Development execution of a stub still emits the expected diagnostic.
- Loaded legacy/debug data containing a stub fails safely without corrupting the
  rest of the loadout.

## Focused rerun package

After all fixes and the full suite pass, export a new exact Windows debug
artifact and create a narrow checklist containing only:

1. executable filename, byte size, SHA-256, version, commit, build time, and
   original BUILD STAMP log;
2. one victory with recorded `Gold earned` and `Total gold`;
3. proof that reopening available menus or reevaluating victory does not award
   twice;
4. keyboard, held keyboard, gamepad, and pointer attempts against the visible
   results overlay, with no cursor movement;
5. Map Menu `Total gold` visibility;
6. an overflowing More Info description scrolled with Page Up/Page Down,
   right stick, and mouse wheel;
7. confirmation that unimplemented skills are absent from release-facing
   choices while the clean-log review distinguishes expected development-only
   diagnostics;
8. explicit final PASS/FAIL and reproduction details for any failure.

Evidence completeness is reviewed manually. Missing fields are not silently
converted into passes.
